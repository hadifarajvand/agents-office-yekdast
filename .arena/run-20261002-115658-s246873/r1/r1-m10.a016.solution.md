## Headline finding: the plan's department scheme does not match the roster on disk, including the full override chain

The plan states repeatedly (merge note, "Current agent stack" section, "Department remap" acceptance line) that `office.agents.json` already has an 8-department structure of **`exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`** — 35 seats, that scheme.

That is false, and I checked the full override chain CLAUDE.md itself documents (`office.agents.json` → `<brain>/Agents Office/agents.json` → `office.agents.local.json`, later wins), not just the base file:

- `office.agents.json`: departments are `content: 3, devops: 5, secdata: 3, revenue: 8, frontend: 4, exec: 3, fin: 3, engineering: 6` (35 total). `success` and `product` do not exist anywhere.
- `office.config.local.json` → `brain: "./brain-yekdast"`. The override file `brain-yekdast/Agents Office/agents.json` exists, but its content is `{"agents": [], "note": "Backup roster. Left empty; auto-populated by office on first run."}` — zero agents, zero department overrides.
- `office.agents.local.json` does not exist.
- Confirmed by the live `npm run check` output itself: `roster: office.agents.json validates — 35 agents · 35 customised · office.agents.json + brain/Agents Office/agents.json` — 35 agents total, matching the base file's count exactly; the brain file supplies customisations (briefs/tools), not new departments or seats.

So the override chain does not and cannot inject `success`/`product` at runtime — the live, served roster really does use `content/devops/secdata/revenue/frontend/exec/fin/engineering`, the same scheme `src/data.js`'s `AGENTS` array uses (same departments, same per-department counts, 35 total). Frontend and backend roster are in sync with each other, just not with what the plan calls "current."

This is corroborated by the git log: the most recent commit (`92de5bd`) is titled *"Backup: snapshot working tree before 8-department/80-seat Citadel redesign"* — the repo is at the pre-redesign snapshot. `.claude/unused-seats.md` and `CLAUDE.md`'s "Department keys" section describe a *third*, even older scheme (`emails/sales/marketing/ops/fin/delivery`, 6 departments). Three generations of department naming coexist in the repo's own docs; the plan's "current" baseline matches none of them — it matches the *target* state two generations ahead of what's on disk.

Consequences that cascade from this:

1. **Task 6b is solving the wrong problem.** The plan says `office.config.local.json`'s `mcp.departments` keys are stale, keyed to `content`/`secdata` instead of "the current" roster. Reading the file directly: every key in it (`content`, `secdata`, `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`) is a **valid, currently-live department** per `office.agents.json`. This file is not stale — it is already correctly wired to the real roster. Task 6b as written would have someone "fix" a config file that isn't broken, by renaming keys to departments (`success`, `product`) that don't exist yet.
2. **Task 2's connector matrix table** (`GitHub → revenue, engineering`, `Gmail → revenue, success`, etc.), captioned "remapped to the current 8-dept roster," is actually remapped to the *Part II target* roster. `success` doesn't exist to grant Gmail access to yet.
3. **The "Department remap" line in Foundation Acceptance** ("matches the current 8-department roster, not the stale 6-department one") sets up a false binary — the live roster is neither the 6-dept scheme nor the plan's assumed 8-dept scheme; it's a third, distinct 8-dept scheme the plan never names.

**What to fix in the plan**: replace every "current department structure is `exec/revenue/engineering/frontend/devops/fin/success/product`" claim with the actual live set (`content/devops/secdata/revenue/frontend/exec/fin/engineering`), drop or substantially rewrite Task 6b, and make explicit in Part II that the `content→?` and `secdata→?` renames are Task 17 rollout work, not an already-done precondition.

   - `smoke: department focus opens the chat rail — rail: left agentOpen`
   - `smoke: approval flow reaches the panel — no waiting row (ada: stuck)`
   - `server: /api/brain has the live graph — empty`

   The plan's claimed baseline (37/38, one pre-existing unrelated failure) is stale or was never true against this working tree — there are three additional, undisclosed smoke-test failures in the live/demo task flow and approval flow. This matters directly: the plan's own Foundation Acceptance checklist uses "`npm run check` ... green" as a gate, and anyone executing Task 1 using the plan's stated baseline as "ground truth, nothing new to investigate" will miss three real, currently-failing UI flows (task creation, chat rail, approval panel) that have nothing to do with the brain-graph issue the plan names.

2. **The 404 contract-table row is wrong.** The plan's API contract table says: `* | anything else | 404 {error:'not found'} | main.py:454-456`. Lines 454–456 are actually:
   ```python
   @app.exception_handler(Exception)
   async def on_error(_req, exc: Exception):
       return JSONResponse({"error": str(exc)}, status_code=500)
   ```
   That's a generic 500 handler for unhandled exceptions, not a 404-for-unmatched-routes handler. There is no explicit catch-all in `main.py` that returns `{"error":"not found"}` with status 404 for an arbitrary unmatched path — FastAPI/Starlette's own default 404 would fire instead. The `{"error":"not found"}`/404 pattern does appear elsewhere (lines 201, 321, 350) but those are all for a missing resource by id within an existing route, not a wildcard route. The contract table's final row should cite the exception handler correctly (500, not 404) or be dropped.

The plan should say "already implemented, confirm it still covers every route in the table below" rather than listing it as a CREATE deliverable.
