## 2. Required corrections — these are real problems

### A. The plan's "current 8-department" premise is false. The redesign it describes as already-landed hasn't landed.

The plan's header states the 8 departments `exec, revenue, engineering, frontend, devops, fin, success, product` "are current and load-bearing throughout." Checked three independent ways against the live repo:

- `backend/app/mcp.py:16`: `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]` — `secdata`/`content`, not `success`/`product`.
- `office.agents.json`'s 35 agents break down as `{revenue:8, engineering:6, devops:5, frontend:4, content:3, secdata:3, exec:3, fin:3}` — same conclusion.
- `src/data.js`'s `LAYOUT` and `BILLBOARDS` are keyed `exec, revenue, engineering, frontend, devops, secdata, fin, content` — same set.

This matches the repo's git history: the current branch tip is `92de5bd Backup: snapshot working tree before 8-department/80-seat Citadel redesign` — the working tree was snapshotted before (or reverted from) that redesign, and the plan was never updated to match. It is describing a department rename (`secdata`→`success`, `content`→`product`) that is not actually in the files it cites.

This falsifies two downstream claims:

- **Task 6b is diagnosing a bug that doesn't exist, and would create one if executed as written.** The plan calls `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, etc.) "stale... pre-redesign keys." I read `office.config.local.json` directly: every department name it uses (`engineering`, `frontend`, `devops`, `secdata`, `fin`, `content`, `revenue`, etc.) is a real, live department key. There is no drift to fix today. Executing Task 6b as written would rewrite a currently-correct config to reference departments (`success`, `product`) that don't exist, actively breaking Task 2's policy gate.
- **Task 11's "Decided (2026-10-02, owner): pilot department is `success`"** names a department not in the roster. Either this decision needs to be re-made against a real department, or the rename needs to be its own explicit, verified task before Task 11 starts. By extension, Part II's whole seat-count table (Product/`product` 6, Customer Support/`success` 5, etc.) is only buildable once `product` and `success` exist.

**Concrete fix**: in the merge note, Task 6b, and the Part II department table, replace `success`/`product` with the real current keys `secdata`/`content` — or insert an explicit, gated rename task before Task 9b/10/11, and only then treat `success`/`product` as real.

### B. The "37/38 passed, one unrelated failure" claim is stale — and the real number is unstable, not just different.

The plan states (twice): *"`npm run check` passes 37/38 (one pre-existing, unrelated failure: `server: /api/brain has the live graph`)"* and concludes *"No application-breaking defects found."*

I ran `npm run check` three times against the current repo and got **three different results**:

```
Run 1: 35/38 — smoke: command bar adds a task in demo mode, smoke: department focus opens the chat rail, server: /api/brain has the live graph
Run 2: 35/38 — smoke: a routine typed in the bar lands in SCHEDULED [passed], smoke: department focus opens the chat rail [failed], server: /api/brain has the live graph [failed]  (3 failures total, counted differently)
Run 3: 34/38 — smoke: command bar adds a task in demo mode, smoke: department focus opens the chat rail, smoke: approval flow reaches the panel, server: /api/brain has the live graph
```

Every run fails `server: /api/brain has the live graph` (the one the plan accounts for), but also at least two of three browser-smoke checks (`command bar adds a task in demo mode`, `department focus opens the chat rail`, `approval flow reaches the panel`) on a non-deterministic basis — the suite is flaky, not just at a different fixed count than the plan states. These failing checks sit directly in the task panel / approval-flow / chat-rail surface area that Foundation Tasks 1, 2, 3, 4, and 7 all touch (Task 7's rationale is built on "`initTasks()` is an 84-edge god node" — these failures are inside that node's territory), and Task 7's contract tests (API request/response shape only) won't catch UI-smoke flakiness.

**Concrete fix**: update the "Current agent stack" and "Application audit" sections to say the smoke suite is currently flaky (34-35/38 across repeated runs, not a fixed 37/38), name the three additional candidate failures, and decide explicitly whether fixing that flakiness is in-scope for Task 7 or needs its own task — rather than letting a stale, falsely-precise "37/38, one failure" stand as the baseline.

### C. Two rows of Task 7's own API-contract table are wrong, not "exact."

The table (plan, Task 7) says:

- `/api/chat` → `{reply, read, tools, used, interview, routine?, routines?, setup?}` — `main.py:423-452`
- `* anything else` → `404 {error:'not found'}` — `main.py:454-456`

I read `backend/app/main.py:423-456` directly. The real `/api/chat` handler only ever returns `{"reply": reply}` (or an early `{"reply": ...}` for a routine/schedule command, or `{"error": "unknown agent"}` with status 400) — there is no `read`, `tools`, `used`, `interview`, `routine`, `routines`, or `setup` key anywhere in the function. And lines 454-456 are `@app.exception_handler(Exception)` returning a 500 on any uncaught exception — there is no catch-all 404 route anywhere in `main.py`.

This matters specifically because Task 7 is the plan's own "cheapest test to write, highest-value regression guard" — the first thing anyone executing this plan would build — and it would be built directly from this table. As written, Task 7 would either need someone to notice the table is wrong before writing the test, or it would ship a contract test asserting a response shape and a 404 behavior the backend does not actually produce.

**Concrete fix**: correct the `/api/chat` row to `{reply}` (plus the early-return `{reply}` and `{error}` 400 cases), and correct the 404 row to describe the actual behavior — an `Exception` handler returning 500, with no explicit 404 catch-all — before Task 7 is built from this table.
