# Validation Report: `agents-office-implementation.plan.md` vs. current repository

## Assumptions
- "Current state of the repository" means the working tree as it sits on `main` right now (verified via direct file reads, `npm run check`, and `git log`), not any branch the plan's author may have had checked out when writing it.
- Where the plan cites a line range and the actual boundary is off by 1–2 lines (e.g. a decorator line vs. the function body), I treat that as accurate and don't flag it as a discrepancy — only genuine mismatches are reported as findings.

## Headline finding (affects categories 2, 4, 6, 7, 9)

**The plan's department-name baseline is factually wrong.** The plan states, in its preamble and again in §"Current agent stack": *"Department names and count (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout."*

That is not what's on disk. The actual current department set, confirmed in three independent places that must agree with each other and do:
- `office.agents.json` — seat counts by dept: `content: 3, devops: 5, secdata: 3, revenue: 8, frontend: 4, exec: 3, fin: 3, engineering: 6` (35 total).
- `backend/app/mcp.py:16` — `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`.
- `src/data.js:17` — `DEPT_KEYS = ['exec', 'revenue', 'engineering', 'frontend', 'devops', 'secdata', 'fin', 'content']`, and its `LAYOUT` object (line 80) keys plinths the same way.
- `npm run check`'s own smoke output confirms "eight department cards" against this same 8-dept set.

So today's 8 departments are `exec, revenue, engineering, frontend, devops, secdata, fin, content` — **not** `exec, revenue, engineering, frontend, devops, fin, success, product`. `secdata` and `content` exist; `success` and `product` do not exist anywhere in the roster, the backend, or the frontend data layer. The most recent commit is titled *"Backup: snapshot working tree before 8-department/80-seat Citadel redesign"* — i.e. the repo being validated against is a pre-redesign snapshot. The plan was written as if the department rename to `success`/`product` had already landed; it hasn't.

Everything downstream that assumes `success` and `product` exist today inherits this error — see categories 2, 4, 6, 7, 9 below.

There is also a third, older scheme still present in checked-in docs: the project's own `CLAUDE.md` (repo root) and `.claude/unused-seats.md` describe a *different* 6-department, 35-seat baseline (`emails, sales, marketing, ops, fin, delivery`, caps 5/6/7/6/4/7) that matches neither the plan's claimed baseline nor what's actually in `office.agents.json` today. The plan doesn't mention this third scheme at all (category 9), since whoever picks up Task 6/6b will hit three mutually inconsistent sources of truth, not two.

## 8. UI/layout claims — **line citations accurate; collision-margin arithmetic independently verified and matches**

- `src/main.js` — confirmed `const COLS = Object.fromEntries(DEPT_KEYS.map(k => [k, 2]))` at line 199 (plan says "lines 198-206," off by one; the 8.6/6.4-unit spacing constants the plan cites are confirmed present at lines 205–206). Close enough to call accurate.

Their current depths differ (28 vs 26), which the plan's shared "~38.4 unit depth / ~4.8 unit margin" figure treats uniformly — worth flagging as a simplification, but not disqualifying.
- **The margin arithmetic is independently reproducible from `LAYOUT` alone, with no rotation/scene-geometry data needed**, because `LAYOUT`'s positions are already flat world-XZ coordinates (per its own comment). Worked example along the z-axis: `engineering` at `pos.z=12, d=28` has z-extent `[12-14, 12+14] = [-2, 26]`; its ring neighbor toward the "depth growth" direction sits at z-center 48 with half-depth 12, giving extent `[36, 60]`; the gap is `36 − 26 = 10` units — matching the plan's claimed current margin exactly. Post-change, with `d` growing to 38.4 (half 19.2), the new extent is `[12−19.2, 12+19.2] = [−7.2, 31.2]`, and the new gap is `36 − 31.2 = 4.8` units — matching the plan's claimed post-change margin exactly. So the plan's headline "~10 → ~4.8" figure is in fact independently checkable from `LAYOUT` and is correct for at least one axis/neighbor pairing; the open item is only whether it's uniformly correct for *both* 14-seat departments given their differing starting depths (28 vs 26), which the plan should show per-department rather than as one shared number.
- The plinth-width question Task 16 leaves open is, as the plan says, genuinely still open — no width-equivalent computation exists anywhere in `LAYOUT` or `main.js` that would have already answered it.

## Overall verdict

**This plan is not a reliable basis to start executing Task 1 onward right now**, for two independent reasons:
1. Its single most load-bearing factual claim — the current department names — is wrong, and that error propagates into Task 2's connector matrix, Task 6/6b's entire premise, Task 11's pilot-department choice, and the 70-seat target table's department identifiers (categories 2, 4, 6, 7, 9).
2. Its own "Files to Change" table contradicts its own Task 7/ground-truth sections about whether `test_api_contract.py` needs to be created or already exists (category 6/9) — a reader following the table alone would waste effort rewriting a file that's already done, or worse, overwrite a working 310-line test suite.

Everything else — every backend file:line citation, every API contract entry, the `npm run check` 37/38 result and its exact failure message, the dependency/infra claims, the decided-vs-open bookkeeping, and the Task 16 margin arithmetic (independently re-derived and confirmed exact) — checked out as accurate on direct inspection. One frontend behavioral claim (`applyRoster` patching `tools`) is false.

**Concrete corrections needed before this plan is safe to execute:**

1. **Preamble + "Current agent stack" section**: replace the claimed current department set `exec, revenue, engineering, frontend, devops, fin, success, product` with the actual current set `exec, revenue, engineering, frontend, devops, secdata, fin, content`. State explicitly whether `secdata`→`success` and `content`→`product` are intended renames, with a migration step for existing seats, or whether `success`/`product` are net-new departments replacing them outright.
2. **Task 6b**: rewrite its premise. `office.config.local.json`'s `mcp.departments` keys (`content`/`secdata`/etc.) are **not** stale relative to the current roster — they match it. The actual gap is that the plan's own target scheme (`success`/`product`) doesn't exist anywhere yet. Task 6b should become "decide and execute the `secdata`/`content` → `success`/`product` rename (if that's the decision) across `office.agents.json`, `mcp.py:16`'s `DEPT_KEYS`, `src/data.js:17`'s `DEPT_KEYS` and `LAYOUT`, and `office.config.local.json`'s `mcp.departments`, keeping all four in lockstep" — not "fix stale keys."
3. **Task 2's connector matrix**: its department column needs the same correction once #1 is decided — right now it's written against departments that don't exist in `mcp.py`'s `DEPT_KEYS`.
4. **Task 11 (pilot)**: "pilot department is `success`" is not actionable until #1 is resolved, since no such department exists today.
5. **Files to Change (Foundation) table**: change `backend/tests/test_api_contract.py`'s row from `CREATE` to `VERIFY`/`EXTEND` (it already exists, fully implemented, at 310 lines) — this contradicts Task 7's own "contract is already implemented" line and the ground-truth section's own file list.
6. **Task 9b**: correct the claim that `applyRoster()` "already live-patches name/role/does/tools." It patches name/role/does (via `tagline`) and greeting/chips, but **not** `tools` — add `tools` handling to Task 9b's scope rather than assuming it's already covered.
7. **Task 6**: add a line noting the root `CLAUDE.md`/`unused-seats.md` 6-department scheme as a third source of truth that also needs reconciling, not just the two-source conflict the plan currently frames.
8. **Task 16**: either compute the collision margin separately for Backend Engineering (depth 28→38.4) and Infrastructure & QA (depth 26→38.4) since they start from different depths, or explicitly state the single ~4.8-unit figure is a shared worst-case estimate rather than a per-department computed result. Note that the ~10→4.8 figure itself *is* independently verifiable from `LAYOUT`'s world-XZ coordinates (worked out in §8 above) and is correct for at least the engineering axis checked.

Everything else — the Foundation tasks' technical content (checkpointer, policy gate, redaction, `interrupt()`, Redis scheduling, E2E smoke, legacy retirement), the API contract table, and the dependency/infra setup — is accurate as written and can proceed once the corrections above are made.
