### Stale / inconsistent / false — this is the plan's central, load-bearing defect

**The plan's department-name claim is factually wrong against the current repo, in both directions it needs to be right.**

The plan states (header, lines 12 and repeated at line 211, 234-248, 252, 300, etc.): *"Department names and count (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout."* It further asserts (lines 20, 24, 127-131) that `office.config.local.json`'s `mcp.departments` keys — `content`, `secdata`, etc. — are **stale, pre-redesign department names that don't match the current roster**, and builds Task 6b around rewriting them to the `exec/revenue/engineering/frontend/devops/fin/success/product` set.

This is backwards. Checking the actual code:
- `backend/app/mcp.py:16`: `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`.
- `backend/app/roster.py:31` (comment): *"...so this matches routines.mjs's DEPT_KEYS (exec/revenue/engineering/frontend/devops/secdata/fin/content)."*
- `office.agents.json`'s 35 agents break down by department as: `revenue:8, engineering:6, devops:5, frontend:4, content:3, secdata:3, exec:3, fin:3` (verified by direct count) — `content` and `secdata` are real, populated departments today; `success` and `product` do not exist anywhere in the roster, `mcp.py`, or `src/data.js`.
- `src/data.js`'s `LAYOUT` and `BILLBOARDS` tables are keyed by the same 8 names: `exec, revenue, engineering, frontend, devops, secdata, fin, content` — again, `success`/`product` appear nowhere.
- `npm run check`'s own smoke output confirms "eight department cards" against this same `content`/`secdata`-bearing roster.

So: `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, plus `exec/revenue/engineering/frontend/devops/fin`) are **exactly the current department set**, not a stale pre-redesign one. There is no confirmed bug here for Task 6b to fix as described. What actually doesn't exist anywhere in the current repo is `success` and `product` — those are *target* names for the 70-seat Org Redesign (Part II), not the *current* 8 departments the plan's Foundation section (Part I) claims they already are. The plan has conflated its own target-state naming with the current-state naming and then, on that false premise, invented a "fix" for a config file that was actually correct. This affects:
- Task 6b in full (the "fix" would break a currently-correct file by renaming `content`→`success`/`secdata`→`product`, before any seat in those departments has actually been renamed).
- Task 2's connector matrix table (lines 83-93), which is written against `exec/revenue/engineering/frontend/devops/fin/success/product` — it needs to be rewritten against the real current keys (`content`, `secdata`) for it to be enforceable today, and re-derived again once Task 17 actually renames departments.
- Task 6's "Note (department remap)" (line 123), which tells the implementer to "re-derive [AGENTS.md's 12 agents'] current department from the current 8-dept table (e.g. an agent that was `sales` is now `revenue`)" — `sales` isn't even in the picture; `.claude/AGENTS.md`/`.claude/unused-seats.md` actually describe a **third, older 6-department scheme** (`emails, sales, marketing, ops, fin, delivery`, 35 seats — this is also what the project's own `CLAUDE.md` describes), which matches neither the plan's claimed current 8-dept set nor the actual current 8-dept set in code. The remap is at minimum a two-generation jump (6-dept legacy docs → 8-dept actual code → 8-dept *target* names in this plan), not the one-hop rename the plan implies.
- The Foundation header's claim (line 12) that department names are "current and load-bearing throughout" needs to be split: `exec/revenue/engineering/frontend/devops/fin` are current; `success`/`product` are target-only (today's equivalents are `secdata`/`content`).

**The plan's `npm run check` suite-size claim is also wrong, independent of the pass count.** The plan states (line 28) that the audit instrument includes "a full in-browser smoke suite (23 checks), and 8 live-server checks." Opening `check.mjs` directly:

**`npm run check`'s pass/fail count is a flaky number, not a stable fact, and the plan is wrong to hard-code a single result.** The plan states (lines 20, 26-32) *"`npm run check` passes 37/38 (one pre-existing, unrelated failure: `server: /api/brain has the live graph`)."* Running it four times from this same working tree just now produced four different results: 37/38 (only `/api/brain`), 36/38 (`/api/brain` + "command bar adds a task in demo mode"), 34/38 (`/api/brain` + three other UI-smoke checks), and 35/38 (`/api/brain` + "department focus opens the chat rail" + "approval flow reaches the panel"). ## Overall verdict

**Not yet reliable as a basis to start Task 1 onward right now.** Two load-bearing defects need fixing first: the department-naming conflation (current vs. target names), and the suite-size/pass-count claims about `npm run check` (both the "23 smoke / 8 server checks" composition and the exact "37/38" pass count are wrong — the latter because the suite is genuinely flaky, confirmed by four different results across four consecutive runs just now).

The plan's backend code citations (file paths, line ranges, function names) remain consistently accurate on re-check — this is not a plan that was never checked against the repo for most of its claims. The problems cluster specifically around department naming and the one audit-instrument claim (`npm run check`'s composition and result) that turned out to need more scrutiny than a single run gives it.
