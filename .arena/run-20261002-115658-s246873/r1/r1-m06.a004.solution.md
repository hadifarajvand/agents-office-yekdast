# Validation report: `agents-office-implementation.plan.md` vs. the repository as it actually stands today

## Bottom line first (for whoever has to act on this)

**Do not start Task 1 on this plan as written.** The plan's entire account of "the current 8-department roster" is wrong, and that error is load-bearing — it's cited as fact in the header, the Foundation ground-truth section, Task 2's connector matrix, Task 6/6b, and the whole Part II seat-count table. Everything else I checked (file inventory, API contract line numbers, `engine.py`/`mcp.py`/`models.py` line numbers, `requirements.txt`, `docker-compose.yml`) is accurate and can be trusted as-is. The one correction below (department scheme) has to be made before anyone assigns Task 2 or Task 6b, because both are written against a roster that doesn't exist. There is also a second, separate issue: the `npm run check` smoke suite is flaky, so the plan's single fixed "37/38" baseline cannot be trusted as a stable number either way (see §2).

---

## 1. The department-scheme claim is false — this is the plan's central defect

The plan states, repeatedly and as settled fact: *"Department names and count (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout"* (plan, Part I header) and *"`office.agents.json` has the 8-department structure applied (35 seats today)"* (Foundation ground-truth section).

That is not what's in the repository. I read `office.agents.json` directly and counted:

```
3 content
5 devops
6 engineering
3 exec
3 fin
4 frontend
8 revenue
3 secdata
```

8 departments, 35 seats — but the names are `exec, revenue, engineering, frontend, devops, fin, content, secdata`. **There is no `success` department and no `product` department anywhere in the current roster.** This isn't a one-off typo — it's confirmed independently in three more places in the backend itself:

- `backend/app/mcp.py:16` — `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`
- `backend/app/roster.py:31` — a comment explicitly states this matches `routines.mjs`'s `DEPT_KEYS (exec/revenue/engineering/frontend/devops/secdata/fin/content)`
- `src/data.js:17` — `export const DEPT_KEYS = ['exec', 'revenue', 'engineering', 'frontend', 'devops', 'secdata', 'fin', 'content'];` (single line; `LAYOUT`'s plinth keys further down the file use the same set)

So `success`/`product` are not a renaming the plan proposes going forward (Part II is explicit that department *names* don't change, only seat counts do) — they're presented as the plan's description of *today's* state, and today's state is actually `content`/`secdata`, not `success`/`product`. This means:

- **Task 2's connector matrix** (the table mapping GitHub/GitLab/Slack/Gmail/Notion/Docker/Prometheus/Grafana to departments) is written against `success` and `product`, neither of which exist. It needs to be rewritten against `content` and `secdata` before anyone implements it.
- **Task 6b** ("fix `office.config.local.json`'s stale `mcp.departments` keys") is built on a false premise. I read `office.config.local.json` directly — its `mcp.departments` keys are `github, gitlab, slack, gmail, notion, docker, prometheus, grafana`, and the department values inside them (`engineering, frontend, devops, revenue, secdata, fin, exec, content`) **exactly match** `office.agents.json`'s real department set. The file is not stale. The plan's claim that it's "keyed to pre-redesign department names (e.g. `content`, `secdata`)" has it backwards: `content` and `secdata` *are* the current, correct names. Task 6b as scoped should not be executed — there is nothing to fix there. (The plan's Part II seat table does propose folding `content` into `revenue` and renaming `secdata`-adjacent concerns away — but that's a Part II decision not yet made or executed, and Task 6b's "fix" would actively break the config by rewriting correct keys to names that don't exist yet.)
- **Part II's whole seat-count table** (Leadership/`exec` 7, Sales & Marketing/`revenue` 13, Product/`product` 6, Backend Engineering/`engineering` 14, Frontend Engineering/`frontend` 6, Infrastructure & QA/`devops` 14, Customer Support/`success` 5, Finance/`fin` 5) silently assumes `content` and `secdata` have already been retired in favor of `product` and `success`. That retirement is never stated as a task anywhere in the document. Someone executing this plan literally cannot write Task 17's roster without first deciding what happens to the `content` and `secdata` seats and names — and the plan gives no guidance because it doesn't know this decision is still open.

There's a third, independent scheme in play too: the project's own `CLAUDE.md` (checked into the repo root) describes "Department keys: `emails` (5 seats) · `sales` (6) · `marketing` (7) · `ops` (6) · `fin` (4) · `delivery` (7)" — six departments, generic-product names, none of which match either the plan's `success`/`product` claim or the actual `content`/`secdata` roster. This is a separate, pre-existing drift (the repo's own docs disagree with its own roster) that the plan partially notices but doesn't fully resolve — see §3 below.

**Correction needed**: Every reference to `success` and `product` as current department names (plan header, Foundation ground-truth section, Task 2's connector matrix, Task 6b, and the Part II seat-count table) must be changed to `content` and `secdata` respectively, or the plan must add an explicit new task ("rename `content`→? and `secdata`→`product`/`success`, migrate all seats and config keys") before Task 6b or Task 17 can be executed as written.

## 2. `npm run check` claim is stale, AND the suite itself is flaky — any single fixed number is the wrong kind of fact to rely on

The plan states: *"Ran the full check suite... Result: 37/38 passed. The one failure — `server: /api/brain has the live graph` reporting 'empty'... Everything else is green."*

I ran `npm run check` three separate times while preparing this report (once for the original pass, once after re-review, once just now) and got **three different results**:

```
Run A: 36/38 passed — ✗ smoke: command bar adds a task in demo mode, ✗ server: /api/brain has the live graph
Run B: 34/38 passed — ✗ smoke: command bar adds a task in demo mode, ✗ smoke: department focus opens the chat rail,
                       ✗ smoke: approval flow reaches the panel, ✗ server: /api/brain has the live graph
Run C: 35/38 passed — ✗ smoke: command bar adds a task in demo mode, ✗ smoke: department focus opens the chat rail,
                       ✗ server: /api/brain has the live graph
```

The common thread across all three runs: `server: /api/brain has the live graph` fails every time (exactly as the plan already flags, and unrelated to this plan's scope), and `smoke: command bar adds a task in demo mode` also fails every time — this second failure is real, current, and **not mentioned anywhere in the plan's 37/38 baseline**. But the other two smoke failures (`department focus opens the chat rail`, `approval flow reaches the panel`) only show up intermittently, which means the browser smoke suite is flaky — the exact pass count on any given run is not a stable fact to cite, and the plan's single "37/38" figure (and any single replacement number, including an earlier draft of this report's own "36/38") is the wrong kind of claim to make categorically. The right finding is: **the baseline is stale (there is at least one new, consistently-reproducing failure beyond the plan's single named one), and the suite has demonstrated flakiness that the plan does not account for at all.**

One claim in the plan's "Application audit" section does hold up exactly as stated across all three runs: *"the live check output says 'Content, Finance and Revenue'"* — confirmed verbatim every time: `server: a routine outside Emails, Accounting and Sales is refused with a sentence — "Routines come to Engineering in a later release. This release: Content, Finance and Revenue."` So the CLAUDE.md-vs-check-output department-name drift the plan flags is real and current (see §3).

## 3. Internal consistency: the plan's own flagged drift understates the problem

The plan's "Application audit" section says: *"The routine-gating department names in `CLAUDE.md` vs. the live check output's own wording have already drifted from each other (`CLAUDE.md` says 'Emails, Accounting and Sales'; the live check output says 'Content, Finance and Revenue') — reconcile this as part of Task 6."* This correctly identifies that a drift exists, but frames it as a simple wording reconciliation. It is not — it's the same root problem as §1: the live roster uses `content`/`fin`/`revenue` as real department ids, while `CLAUDE.md` (and the plan's own "current 8-department" claim) uses names (`emails`/`sales`/`success`/`product`) that don't exist in the roster at all. Task 6's scope ("reconcile the routine-gating department-name drift... as part of this task") needs to be read as "decide and execute a real department rename," not "fix a comment," or it will under-deliver.

## Overall verdict

**Not ready to execute as-is.** The API-contract, file-inventory, and backend-line-number portions of this plan (Foundation Task 7's contract table in particular) are verified accurate in full and can be trusted directly — that is the majority of the document by volume and it holds up well. But the plan's foundational claim about *what the current 8 departments are called* is wrong, and that error propagates into Task 2's connector matrix, Task 6b's entire premise, Task 6's reconciliation scope, and Task 11's pilot-department choice, and it leaves Part II's whole seat-count table resting on an undocumented, unexecuted rename. There is also a second, independent problem with the plan's `npm run check` baseline: it cites a single fixed number that is both stale and — as this review's own three repeated runs show — inherently unstable, because part of the browser smoke suite is flaky. Concrete corrections needed before Task 1 starts:

1. **Everywhere the plan says the current departments are `exec, revenue, engineering, frontend, devops, fin, success, product`**, correct this to `exec, revenue, engineering, frontend, devops, fin, content, secdata` — specifically the Part I header line, the Foundation ground-truth section, and the Part II "Current department/seat-count target" table's department-key column.
2. **Delete or completely rewrite Task 6b.** `office.config.local.json`'s `mcp.departments` keys are not stale — they correctly match the live roster's `content`/`secdata`-based scheme. There is no bug to fix here today. If the owner does want to rename `content`→ (Content/Marketing, folded into `revenue` per Part II) and `secdata`→`success`/`product`, that needs to be a new, explicit task with its own migration steps (roster edits, config key rewrites, `check.mjs` updates) — not framed as "fixing a stale config."
3. **Rewrite Task 2's connector matrix** to use `content`/`secdata` instead of `success`/`product` until/unless the rename in (2) happens first.
4. **Do not replace the plan's "37/38" with any other single fixed number.** Instead, have whoever starts Task 1 re-run `npm run check` a few times and record it as: `server: /api/brain has the live graph` and `smoke: command bar adds a task in demo mode` fail consistently (treat both as real, current, in-scope-for-Task-7 failures — the plan only names one of them); `department focus opens the chat rail` and `approval flow reaches the panel` fail intermittently (flaky, worth a follow-up ticket on the smoke harness itself, separate from this plan's scope).
5. Treat Task 16's ~4.8-unit margin figure as **unverified** (the plan already says to re-check it before Task 17; this review wasn't able to independently confirm or refute it either, so it stays an open item, not a confirmed one).

Everything else — the backend module/test inventory, the full API contract table, `engine.py`/`mcp.py`/`models.py` line citations, `requirements.txt`/`docker-compose.yml` dependency claims, and the Part I/Part II gating consistency — checks out against the repository as it stands today and can be executed from as written.
