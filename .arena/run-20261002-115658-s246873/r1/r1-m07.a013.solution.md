# Validation report: `agents-office-implementation.plan.md` vs. the current repository

## Headline finding (overrides most of the plan's "ground truth" section)

The plan's foundational claim — "`office.agents.json` has the 8-department structure applied... Department *names* and *count* (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout" (plan lines 12, 18-20) — **is false against the repo as it stands right now.**

`office.agents.json` today has 35 agents across 8 departments, with keys:

```
content: 3, devops: 5, secdata: 3, revenue: 8, frontend: 4, exec: 3, fin: 3, engineering: 6
```
(verified directly by loading the JSON and counting departments)

That is `content` and `secdata`, not `success` and `product`. These are exactly the keys the plan calls "pre-redesign" and claims are stale *only* in `office.config.local.json`'s `mcp.departments` (plan line 24, Task 6b). They are not stale leftovers in a side config — they are the live department identity of every agent in the roster, baked into `src/data.js`'s `LAYOUT`/`DEPT_META`/roster entries (lines 20-22, 81-89, 95-103, keyed `secdata`/`content` throughout) and into the department-card smoke check (`npm run check` reports "eight department cards" against this same 8-key set).

The strings `success` and `product` do not appear as department keys anywhere in `office.agents.json` or `src/data.js`. The most recent commit before this plan was written is titled **"Backup: snapshot working tree before 8-department/80-seat Citadel redesign"** (`git log`, commit `92de5bd`, 2026-10-02). That message, by its own wording, documents that the `exec/revenue/engineering/frontend/devops/fin/success/product` scheme the plan treats as *already live* is the thing that redesign has **not yet executed** — the repo is still on the pre-redesign scheme (`content`/`secdata` instead of `product`/`success`, and the mapping isn't even 1:1: nothing in the plan says which old department becomes `product` and which becomes `success`).

**Consequence**: every downstream claim depending on "the current 8-department roster already being `exec/revenue/engineering/frontend/devops/fin/success/product`" is built on a false premise — most importantly Task 6b and the "Current department/seat-count target" table in Part II.

- **70-seat target table** (Leadership 7, Sales & Marketing 13, Product 6, Backend Engineering 14, Frontend Engineering 6, Infrastructure & QA 14, Customer Support 5, Finance 5 = 70): a forward-looking target, so not "wrong" per se — but it rests on `product` and `success` already existing as live department identities, which they don't. `secdata` and `content` are the two departments that would need renaming/repurposing, and the plan never says which becomes which. Task 11 (pilot, decided as `success`) and Task 17 (full rollout) both assume `success` is a live key today that merely needs more seats. It isn't — anyone executing Task 11 literally would find no `success` department and be blocked immediately on an unstated prerequisite.

- **Sequencing consequence, now cited precisely**: the plan's own "Foundation Execution grouping" table places Task 6b in **Group C** together with Tasks 2 and 3 ("C — Policy & tools | 2, 3, 6b | ... not against stale connector-department keys | B", plan line 206), and Task 2's own entry states "**Depends on**: Task 6b (below) landing first, or in the same pass" (plan line 80). ## 8. UI/layout claims — arithmetic check

- `COLS = 2` and 8.6/6.4 spacing at `src/main.js` ~198-206: **confirmed** (see §1).
- `src/data.js` `LAYOUT` depths: `engineering: pos:[46,12], d:28`; `devops: pos:[-12,56], d:26`; `revenue: pos:[40,-28], d:32`. **`revenue` currently has the single deepest footprint in `LAYOUT` (d:32)**, deeper than both departments (`engineering`, `devops`) the plan singles out for the 3-column treatment — and `revenue` is also growing by 5 seats (8→13) under the target table, a change Task 16 never revisits. This is a real scope gap in Task 16 as written.
- **Collision-math check, done directly from `LAYOUT` (correcting the previous draft of this report, which wrongly called this unverifiable)**: `engineering`'s z-range today is `pos.z ± d/2 = 12 ± 14 = [-2, 26]`. Its ring-neighbor `revenue`'s z-range is `-28 ± 16 = [-44, -12]`. The gap between them is `-2 - (-12) = 10` units — **exactly matching the plan's claimed "~10 units" current margin**. Growing `engineering`'s depth to the plan's proposed ~38.4 units (keeping its center fixed) gives a new z-range of `12 ± 19.2 = [-7.2, 31.2]`; the gap to `revenue` becomes `-7.2 - (-12) = 4.8` units — **exactly matching the plan's claimed post-change "~4.8 units" margin**. The plan's arithmetic is confirmed correct using only the repo's own `LAYOUT` data, with one caveat: this computation assumes `revenue`'s own footprint stays at `d:32` while it simultaneously grows from 8→13 seats under the target table, which Task 16 doesn't address (see the `revenue` gap noted above) — if `revenue`'s depth also grows, the 4.8-unit margin could shrink further than the plan states.

## Overall verdict

**This plan is not a reliable basis to start executing Task 1 onward right now, as written**, for two reasons:

1. **Structural**: the "ground truth" framing — that the repo is already on the target 8-department scheme and that `office.config.local.json`'s keys are the only stale thing left (Task 6b) — is backwards. The repo is still on the pre-redesign scheme (`exec/revenue/engineering/frontend/devops/secdata/fin/content`), confirmed directly via `office.agents.json` and `src/data.js`, and by the repo's own last commit message. Task 6b (Group C, co-gating Task 2 per plan lines 80 and 206) should be removed from the Foundation group or re-scoped as a post-Task-17 cleanup step — there is nothing stale to fix in that file today.
2. **Factual/process**: the plan's single static `npm run check` snapshot ("37/38, one pre-existing unrelated failure") doesn't hold up as a stable fact — repeated runs on an unchanged tree flip between 36/38 and 37/38. The plan should note the suite's flakiness and treat `/api/brain has the live graph` (the one failure that reproduces every time) as the one real, actionable pre-existing defect, rather than asserting a single fixed count.

**Concrete corrections needed before execution**:
- Rewrite the "Current agent stack — ground truth" section (lines 18-24) to state the actual current department keys (`exec, revenue, engineering, frontend, devops, secdata, fin, content`), and separate "current" from "target (post-Task 17)" naming throughout the document, including the Connector matrix table (Task 2, line 85) which lists `success` as if it already exists.
- Rewrite Task 6b (lines 127-131) to either remove it from Foundation Group C entirely, or re-scope/re-gate it as an Org-Redesign step that runs after Task 17's department rename.
- Replace the single "37/38" claim (lines ~20, 30, 32) with a note that the smoke suite is flaky run-to-run and that `server: /api/brain has the live graph` is the one failure that reproduces consistently; investigate that one specifically rather than assuming "no application-breaking defects."
- State explicitly which current department (`secdata` or `content`) becomes `success` and which becomes `product` before Task 11/Task 17 can be executed as written.
- Clarify Task 10's dependency on Task 6 in its own "Gated on" line (line 294), since Task 6 sits in Group D (gated only on Group B) while Task 10 claims to be gated only on Tasks 1-2 (Group B/C) — as written, Task 10 could start before Task 6 lands.
- Note in Task 16 that `revenue` (not just `engineering`/`devops`) currently has the deepest `LAYOUT` footprint (`d:32`) and is also growing 8→13 seats; its geometry should be re-checked alongside the two departments the task already covers. The 10→4.8-unit margin arithmetic itself is independently confirmed correct against `src/data.js`'s current `LAYOUT` values.

Everything else audited — the API contract table, the backend/test file inventories, `requirements.txt`, `docker-compose.yml`, the blocking/async route split, the LangGraph engine code structure, and the decided-vs-open item labeling — checks out accurately against the repo as it stands today.
