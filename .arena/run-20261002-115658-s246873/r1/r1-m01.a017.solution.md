## Headline finding — the plan's department-name ground truth is wrong

The single most consequential error in the document: **the plan repeatedly asserts the current and target department set is `exec, revenue, engineering, frontend, devops, fin, success, product`** (plan lines 12, 20, 234–246, Task 11's pilot pick, Task 16/17's "Backend Engineering/Infrastructure & QA" framing). This is false for *today's* roster on two separate counts:

1. **`office.agents.json`** (35 agents, confirmed by direct read) actually uses departments `exec(3), revenue(8), engineering(6), frontend(4), devops(5), secdata(3), fin(3), content(3)` — 8 departments, 35 seats (seat/department-*count* claim is right), but the 7th and 8th keys are **`secdata` and `content`**, not `success` and `product`. There is no `success` or `product` department anywhere in the roster.
2. Backend code hard-codes the same set independently, in three places: `backend/app/mcp.py:16` — `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`; `backend/app/roster.py:31`'s comment ("matches routines.mjs's DEPT_KEYS (exec/revenue/engineering/frontend/devops/secdata/fin/content)"); and `src/data.js:80-90`'s `LAYOUT` object, which has `exec`, `revenue`, `engineering`, `frontend`, `devops`, `secdata`, `fin`, `content` entries and **no** `success`/`product` entries at all.
3. A third, *different*, and purely documentary scheme sits in the checked-in `CLAUDE.md` at the repo root: **6** departments — `emails(5)`, `sales(6)`, `marketing(7)`, `ops(6)`, `fin(4)`, `delivery(7)` = 35 — which is neither the plan's scheme nor the actual roster's scheme. `.claude/unused-seats.md` independently confirms this same 6-department (`emails/sales/marketing/ops/fin/delivery`) census with the same per-department active/reserved seat counts. This is a stale **documentation** layer, not a third live/executable vocabulary: nothing in `check.mjs`, the backend, or the frontend reads `CLAUDE.md` or `unused-seats.md` to decide what a department is — those files only exist to give Claude Code process instructions. So there are, precisely: **two** functionally live, mutually inconsistent department vocabularies (the actual code/roster's 8-dept `…secdata/content` scheme, and this plan's 8-dept `…success/product` scheme), plus **one** stale documentation layer (`CLAUDE.md`/`unused-seats.md`'s 6-dept scheme) that governs nothing at runtime but is still misleading to a reader. The plan does not mention any of this split anywhere, and its own Task 6 "department remap" note (line 123) only anticipates a *rename within* its own assumed 8-dept table ("an agent that was `sales` is now `revenue`"), not the fact that its destination departments (`success`, `product`) don't exist in the repo at all.

**Concrete consequence:** Task 11's pilot ("pilot department is `success` (5-seat cap)") cannot be executed as written — there is no `success` department to build a 5-seat roster in. Someone has to first decide whether `secdata`→something or `content`→`success`/`product` is the intended rename, and that decision is nowhere in this document.
