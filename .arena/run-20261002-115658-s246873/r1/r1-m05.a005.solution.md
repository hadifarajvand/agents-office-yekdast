## Assumptions
Where the task was ambiguous I took the most literal reading: "validate... based on the current repository" means every concrete, checkable claim (file path, line number, config content, test name, department name, count, arithmetic) gets opened and compared against what's on disk right now, dated 2026-10-02. ## Headline finding: the plan's own "current state" is wrong about department names

The plan states, as a load-bearing fact repeated throughout (line 12, and again in the Org Redesign target-cap table at lines 234–248):

> "Department *names* and *count* (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout."

This is false against the repository today. The actual current department set, confirmed in three independent places:

- `office.agents.json` (read directly): 35 agents across `revenue`(8), `engineering`(6), `devops`(5), `frontend`(4), `content`(3), `secdata`(3), `exec`(3), `fin`(3) — **`content` and `secdata`, not `success` and `product`.**
- `backend/app/mcp.py:16`: `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]` — the code's own canonical department list.
- `src/data.js` (lines 34–75): every agent's `dept` field uses `exec`/`revenue`/`engineering`/`frontend`/`devops`/`secdata`/`fin`/`content` — e.g. `comply`/`recon`/`kmail` are `dept: 'secdata'`, `elead`/`newt`/`cmail` are `dept: 'content'`. Neither `success` nor `product` appears anywhere in the frontend data, the backend code, or the roster.

This single error cascades into the plan's two biggest "confirmed" claims, and — as verified below — into a second, previously unchecked table:

1. **Task 6b is backwards.** The plan claims `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, etc.) are "stale... pre-redesign keys that don't match the current 8-department roster" (lines 24, 128). I read `office.config.local.json` directly: its `mcp.departments` object uses exactly `exec`, `revenue`, `engineering`, `frontend`, `devops`, `secdata`, `fin`, `content` — i.e. it **matches the real current roster exactly, key for key.** There is no stale-key bug to fix. The plan has the direction of the drift backwards: it is the plan's own prose (and the Org Redesign target-cap table) that uses department names (`success`, `product`) which don't exist yet, not `office.config.local.json` that's behind.
2. **Task 2's connector matrix has the identical bug, independently checkable.** Task 2's connector-matrix table (plan lines 83-93) asserts, for Gmail: `Gmail | revenue, success | Draft-only, never send`. The actual current value of `office.config.local.json`'s `mcp.departments.gmail` is `["content", "revenue"]` — not `["revenue", "success"]`. `success` doesn't exist as a department (per the headline finding) and isn't in this list either; `content` is in the list and is simply missing from the plan's table. This is the same department-naming bug reappearing in a second, independently-checkable acceptance table, not a one-off in Task 6b.
3. **The Org Redesign's target-cap table conflates "rename two departments" with "current state."** Reading it charitably, `success` is presumably meant to supersede `secdata` and `product` to supersede `content` (the brain's own `citadel-reference/domain-agent-lists.md` has a `customer-success` domain and a `product-design` domain, which lends some support to that mapping) — but the plan never says this. As written, Task 11's pilot ("pilot department is `success`") and Task 17 ("all 8 departments... Customer Support (`success`) 5... Finance (`fin`) 5") are instructions to build a department that doesn't exist and that no other part of the document tells you how to create (rename `secdata`? add a 9th key and retire `secdata`? the plan's own text says "do not add or remove departments," per `CLAUDE.md`, so a silent 9th key is explicitly disallowed). Anyone executing Task 11 today would stall immediately: there is no `success` department to build a 5-seat roster for.

This is not a minor staleness note — it means Part II cannot be started as written without a prerequisite decision (and probably a Task 9b-adjacent migration task) that the plan doesn't contain: **an explicit old→new department key rename/mapping** (`secdata→success`, `content→product`, and confirmation that `exec/revenue/engineering/frontend/devops/fin` carry over unchanged). Task 6's text gestures at "re-derive their current department from the current 8-dept table (e.g. an agent that was `sales` is now `revenue`)" (line 123) — but `sales→revenue` is *itself* already done in the current roster; the rename this plan actually still needs (`secdata→success`, `content→product`) is never stated, and it would need to touch both Task 6b's and Task 2's config tables once stated.

To be precise about scope: the plan is not merely stale on one fact, it is **internally self-inconsistent** on this point even before comparing to the repo — Task 6b's section treats `content`/`secdata` as the old, wrong names (implying `success`/`product` are already real), while elsewhere nothing in the document ever introduces how `success`/`product` come into existence. The repo-vs-plan drift and the plan's internal inconsistency are two separate, both-true observations, not alternatives.

## Overall verdict

**Not yet an accurate or reliable basis to execute Task 1 onward without corrections.** Part I (Foundation, Tasks 1-9/6b) is in good shape — every specific file/line/test/dependency claim I checked in that half held up, with two real internal inconsistencies (Task 7's `test_api_contract.py` marked `CREATE` when it already exists and is already comprehensive; the "37/38" baseline overstating how stable that number is) and one minor overclaim (`applyRoster()` doesn't patch `tools`). Someone could reasonably start Task 7, 1, or 6b today with only cosmetic corrections, but should not cite "37/38" as a fixed number without re-running the check at execution time.

Part II (Org Redesign) has a real, structural problem, not a cosmetic one: **its entire department-naming premise is wrong against the current repository, and this error recurs in at least two separate acceptance tables.** The plan asserts `exec/revenue/engineering/frontend/devops/fin/success/product` is the current 8-department set; the actual current set is `exec/revenue/engineering/frontend/devops/fin/secdata/content`. Task 6b's fix target (`office.config.local.json`'s department keys) is, when read against the actual file, already correct and matching the real roster — there is nothing to fix there. Task 2's connector-matrix row for Gmail has the same bug (claims `revenue, success`; the file says `content, revenue`). The thing that actually needs fixing is the plan itself: it needs an explicit statement of which current department(s) `success` and `product` are meant to replace (`secdata→success` and `content→product` is the most defensible reading, supported by the Citadel reference's `customer-success`/`product-design` domains, but it is nowhere stated) before Task 2, 10, 11, 12, 14, 16, or 17 — all of which depend on `success` or `product` existing or on the connector matrix being correct — can be executed as written.
