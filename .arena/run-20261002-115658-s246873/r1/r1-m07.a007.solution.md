## Headline finding (affects categories 2, 4, 6, and the plan's own framing)

**The plan's central premise about the current department scheme is wrong.** The plan states, in its header and repeatedly thereafter, that the current 8 departments are `exec, revenue, engineering, frontend, devops, fin, success, product`, and that `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, etc.) are "stale, pre-redesign" keys that need remapping to this scheme.

This is backwards. The actual current department set, confirmed independently in three places, is **`exec, revenue, engineering, frontend, devops, secdata, fin, content`** — there is no `success` or `product` department anywhere in the live repo:

- `office.agents.json` (35 agents): departments are `revenue, engineering, devops, frontend, content, secdata, exec, fin` — 8 departments, 35 seats, and they are `content`/`secdata`, not `success`/`product`.
- `backend/app/mcp.py:16`: `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]` — hardcoded in the policy module itself.
- `src/data.js:17`: `export const DEPT_KEYS = ['exec', 'revenue', 'engineering', 'frontend', 'devops', 'secdata', 'fin', 'content'];` plus full `DEPTS` display names (`SECURITY & DATA`, `CONTENT & COMMS`, etc.), with a dated comment describing an 8-pod "build-and-run" redesign where Emails folded into CONTENT and a new SECDATA pod was split out.

A repo-wide grep for `"success"`/`"product"` as department identifiers across `office.agents.json`, both config files, `src/data.js`, and `backend/app/*.py` returns zero hits. The 8-department, 35-seat redesign the plan treats as historical baseline ("current") is not the one that shipped — a *different* 8-department redesign (the `secdata`/`content` one) is what's actually in the tree.

**Consequences for the plan as written:**
- Task 6b is solving the wrong problem. `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, `revenue`, `engineering`, `devops`, `fin`, `exec` — confirmed by reading the file directly) are **not stale** — they match the live roster and the live `mcp.py`/`data.js` department sets exactly. If Task 6b is executed as specified ("rewrite each to its corresponding current department name"), it would break a config file that currently resolves correctly against every other part of the system.
- Task 2's connector matrix (keyed to `revenue, engineering, devops, fin, success, product`) has two department keys that don't exist. It needs to be rebuilt against the real 8 before it's usable as an acceptance target.
- Task 6's "Note (department remap)" instruction is premised on the same wrong target set.
- Part II's whole target table (mapped to `exec/revenue/product/engineering/frontend/devops/success/fin`) assumes the current roster already has `product` and `success` seats to expand from. It doesn't — it has `content` and `secdata` seats instead, which aren't mentioned anywhere in Part II. Someone executing Task 17 would have no instruction for what happens to the current `content` (3 seats) and `secdata` (3 seats) departments, since those names vanish from the plan's vocabulary.

This is not a cosmetic naming quibble — it is the single fact the plan repeatedly calls "load-bearing," and it does not match the repository.

**Not a reliable basis to start Task 1 onward as written.** The line-level, API-contract, dependency, config-shipped-default, and UI-collision-math claims are almost all independently verified accurate — this plan's authors clearly did real code-reading for most of it, and Part I's Foundation tasks (1-9, 6b) rest on a backend inventory that checks out. But the plan's foundational, repeatedly-asserted claim about *what the current department names are* is wrong, and it is load-bearing across both Part I (Tasks 2, 6, 6b) and the entirety of Part II's target table. Separately, the plan's stated validation baseline (`npm run check` → 37/38, one known failure) is stale against a suite that is itself flaky and should not be replaced with a different fixed number.

1. **Header / "Current agent stack" section**: replace `exec, revenue, engineering, frontend, devops, fin, success, product` with the real current set `exec, revenue, engineering, frontend, devops, secdata, fin, content` everywhere it's asserted as current (header, Task 2's connector matrix, Task 6's remap note, Part II's "Current department/seat-count target" table's key column).
