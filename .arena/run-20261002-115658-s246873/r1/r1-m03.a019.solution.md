## 1. The load-bearing claim that breaks the most things: department names

The plan states, twice, in load-bearing language:

> "Department *names* and *count* (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout." (line 12)
> "`office.agents.json` has the 8-department structure applied (35 seats today...)" (line 20)

**This is false.** `office.agents.json`, `src/data.js`, and `backend/app/mcp.py`'s own `DEPT_KEYS` constant all agree the current 8 departments are:

```
exec, revenue, engineering, frontend, devops, secdata, fin, content
```

`secdata` and `content` appear nowhere being replaced by `success`/`product` today. Grepping the entire repo (`.json/.js/.py`, excluding `graphify-out`/`.arena`) for `"success"` and `"product"` as department-like tokens: zero hits as *current* roster keys — they only exist in Part II's *target* table (lines 241-243) as the names Task 17 will eventually give to renamed departments. Part I's "ground truth" section presents a rename that has **not happened yet** as an accomplished fact, then reuses those department ids as if real throughout Tasks 2, 6, and 6b.

Knock-on effects:
- **Task 6b is built on a false premise.** It says (line 128) `office.config.local.json`'s `mcp.departments` keys are "stale" because they use `content`/`secdata` instead of the current 8-dept set. Reading the file directly: its keys (`github`, `gitlab`, `slack`, `gmail`, `notion`, `docker`, `prometheus`, `grafana`) are wired to exactly `exec/revenue/engineering/frontend/devops/secdata/fin/content` — precisely the **actual** current department set. `office.config.local.json` is not stale against today's roster; it's internally consistent with it. The real gap runs the other direction: it has no entries yet for whatever `success`/`product` become once Task 17 renames things.
- **Task 2's connector matrix** (lines 85-92) is written entirely in terms of `revenue, engineering, devops, fin, product, success` — a department set that doesn't exist in the roster yet. Anyone implementing Task 2 today cannot "remap to the current 8-dept roster" as instructed, because the current roster uses `secdata`/`content`, not `success`/`product`.
- **Task 11's pilot department is "`success`" (line 300)**, chosen because it carries a 5-seat cap in the *target* table. There is no `success` department today — the closest current 5-seat department is `devops`... but by headcount, none of the current departments is guaranteed to map onto whatever `success` becomes. The plan never says which existing department (or seats) becomes the pilot's `success` roster, or when the rename happens relative to Task 17 (full rollout) — which the plan places *after* the pilot. This is a genuine sequencing gap: Task 11 is scheduled before Task 17, yet requires a department key that, by the plan's own account, only comes into existence *during* Task 17.

Separately, the repo's own `.claude/LANGGRAPH-MIGRATION-PLAN.md:177` still describes "the 35-seat/6-department fixed structure from `CLAUDE.md`" (six departments: `emails/sales/marketing/ops/fin/delivery`, per the project `CLAUDE.md`) — a *third*, different department scheme, matching neither the plan's claimed 8-dept set nor the real current 8-dept roster. The plan doesn't address this discrepancy at all, even though it cites `LANGGRAPH-MIGRATION-PLAN.md` as a source.

**Correction needed**: Rewrite the "Current agent stack — ground truth" section and every subsequent department-name reference in Part I to say the real current set (`secdata`, `content`, not `success`/`product`), and restate Task 6b's finding correctly: `office.config.local.json` already matches the current roster; what's missing is forward-looking wiring for the *renamed* departments Task 17 will introduce. Task 11 needs an explicit statement of which existing department/seats become the pilot's `success` roster before Task 17 runs.

## 2. `npm run check`'s browser-smoke block is flaky; the plan's fixed "37/38" baseline cannot be trusted at face value

The plan states (lines 20, 30):
> "`npm run check` passes 37/38 (one pre-existing, unrelated failure: `server: /api/brain has the live graph`...)"

I ran `npm run check` three separate times against the current repo. Results:

- Run 1: `✗ 36/38 — smoke: command bar adds a task in demo mode, server: /api/brain has the live graph`
- Run 2 (re-check): `✗ 34/38 — smoke: a routine typed in the bar lands in SCHEDULED (demo), smoke: department focus opens the chat rail, smoke: approval flow reaches the panel, server: /api/brain has the live graph`
- Run 3: `✗ 36/38 — smoke: department focus opens the chat rail, server: /api/brain has the live graph`

The pass count is **not stable** — it ranges from 34/38 to 36/38 across consecutive runs with no code changes in between, and the specific smoke check that fails rotates (`command bar adds a task in demo mode` / `a routine typed in the bar lands in SCHEDULED (demo)` / `department focus opens the chat rail` / `approval flow reaches the panel`). The **only** consistently-failing check across all three runs is `server: /api/brain has the live graph` — the one the plan already discloses. Everything else in the browser-smoke block is flaky, sometimes passing, sometimes failing with a different name each time.

This means the plan's "37/38, one pre-existing failure" is stale in a more serious way than a simple off-by-one count: the real current state is "one stably-failing check (`/api/brain`), plus an intermittently-failing smoke suite that can knock the total down to 34/38 on a bad run." Any single fixed number — the plan's 37/38, or a corrected 36/38 or 34/38 — misrepresents what's actually going on if stated as a steady-state fact. Since Task 7 (the task the plan schedules first, specifically as "the cheapest test to write... the highest-value regression guard") and the Foundation Acceptance checklist both gate on `npm run check` being green, this flakiness is a real blocker to treating that gate as currently achievable, independent of which exact number is "correct" on any given run.

**Correction needed**: Replace the "37/38" claim with a description of the actual behavior: `/api/brain has the live graph` is the one stably pre-existing, unrelated failure; the browser-smoke block is intermittently flaky across at least four different named checks and should not be treated as a stable 37/38 (or any other fixed number) baseline. Either investigate and stabilize the smoke suite's flakiness before relying on it as Task 7's regression guard, or explicitly document it as flaky and define what "green enough" means for the Acceptance checklist given that flakiness.

## 3. The "Verified API contract" table (Task 7) has two wrong rows

The plan claims this table is "confirmed matching `src/tasks.js`/`src/connectors.js`/`src/main.js` exactly" (line 137) and cites file:line for each row. Two rows are wrong:

- **`POST /api/chat` → `main.py:423-452`**: the plan claims the response shape is `{reply, read, tools, used, interview, routine?, routines?, setup?}`. Reading `main.py:423-451` directly: every code path in `chat()` returns either `{"reply": routines_mod.list_text(...)}`, `{"reply": f'Done — ...'}`, or `{"reply": reply}` from `engine.chat(...)`. There is no `read`, `tools`, `used`, `interview`, `routines`, or `setup` key anywhere in this function. The claimed response shape does not match the actual code at all.
- **`* anything else → 404 {error:'not found'}` → `main.py:454-456`**: lines 454-456 are `@app.exception_handler(Exception) async def on_error(...)` — a generic **500** handler (`return JSONResponse({"error": str(exc)}, status_code=500)`), not a catch-all 404 route. FastAPI's default behavior for unmatched routes is its own 404, which this code doesn't customize at all; there is no explicit `{error: 'not found'}` 404 handler at the cited lines or anywhere else in the file.

Every other row in the table I checked line-by-line against the actual file and they are accurate, including the blocking-vs-async split the plan calls out specifically (`main.py:190-216` blocks; `main.py:219-260` acks immediately via `asyncio.create_task`).

**Correction needed**: Fix the `/api/chat` row to reflect the real `{"reply": ...}`-only shape, and fix the catch-all row to describe the actual generic exception handler (500, not 404) — or note explicitly that FastAPI's default 404 is unverified/unexercised by this table.
