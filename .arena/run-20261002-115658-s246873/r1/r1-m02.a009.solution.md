# Validation report: agents-office-implementation.plan.md vs. current repo

## Assumptions
- "Current repo" means the working tree as it stands right now (uncommitted edits to the plan file included), not the last commit. `git status` shows the plan file itself is modified and untracked `.arena/` exists; neither affects the findings below.
- Where the plan cites a line range loosely (off by 1-3 lines from a function's actual start/end), I count that as a minor drift, noted explicitly below, not treated as a correctness failure — but I state the actual numbers rather than waving the drift through as "confirmed."

## Headline finding: the plan's "current" department set is wrong

The plan states, as load-bearing fact repeated in the merge note (line 12), the Foundation ground-truth section (line 20-24), and the Org Redesign target table (lines 234-248): that the current 8 departments in `office.agents.json` are `exec, revenue, engineering, frontend, devops, fin, success, product`.

This is false. The actual current departments — confirmed in `office.agents.json`, `src/data.js:17` (`DEPT_KEYS`), `backend/app/roster.py:32` (`DEPTS`, derived from the same seed), and the live `npm run check` output — are:

```
exec, revenue, engineering, frontend, devops, secdata, fin, content
```

There is no `success` department and no `product` department anywhere in the current roster, config, or frontend. `src/data.js` lines 10-13 even date-stamp this: *"V4 (1 Oct 2026): full structural redesign — the office moved from a 6-pod go-to-market/ops shape to an 8-pod build-and-run shape... Operations split into EXEC..., ENGINEERING, FRONTEND, DEVOPS and SECDATA. Emails folded into CONTENT."* The repo's own `git log` backs this up: the current HEAD commit is titled *"Backup: snapshot working tree before 8-department/80-seat Citadel redesign"* (`92de5bd`, 2026-10-02 03:18) — the commit this plan shipped in was explicitly taken as a pre-redesign snapshot. `secdata`/`content` are not "pre-redesign" names the plan needs to clean up; they are the department names in production right now, one day after the V4 redesign the plan itself doesn't mention.

This single error cascades into several of the categories below.

### 2. Structural/roster claims — partially wrong

- Seat count: **confirmed** — 35 seats today (`office.agents.json`, `npm run check`'s `roster: office.agents.json validates — 35 agents`).
- Department *count* (8): **confirmed**.
- Department *names*: **wrong**, per above — it's `secdata`/`content`, not `success`/`product`.
- Current per-department seat distribution (verified directly, `python3 -c "Counter(a['department'] for a in json.load(open('office.agents.json'))['agents'])"`): `revenue: 8, engineering: 6, devops: 5, frontend: 4, content: 3, secdata: 3, exec: 3, fin: 3` (sums to 35). Neither `engineering` nor `devops` is anywhere near a 14-seat cap today — 14 is Part II's *target* cap for those departments, not a present-day fact about them. Any claim treating 14 as today's state for either department is false; the plan itself does not make this error (it correctly frames 14 as the target), so this is a caution for whoever reads the plan's target table, not a defect in the plan text itself.
- 70-seat target table (Leadership 7 / Sales & Marketing 13 / Product 6 / Backend Eng 14 / Frontend Eng 6 / Infra & QA 14 / Customer Support 5 / Finance 5 = 70): internally consistent arithmetic (7+13+6+14+6+14+5+5=70), but it's captioned "Current department/seat-count target" against department *keys* (`exec`/`revenue`/`product`/`engineering`/`frontend`/`devops`/`success`/`fin`), two of which (`product`, `success`) don't exist. Either this table silently assumes `secdata`→`success` and `content`→`product` renames that are never stated as a task anywhere in the plan, or the plan was written against a different (later, not-yet-committed) snapshot of the roster than the one actually in the repo. Either way, as written, nobody can execute Task 17 against this table without first answering "do `secdata` and `content` get renamed, and if so, where's that task?"

### 4. Config claims — the core Task 6b premise is backwards

- `office.config.json` ships with empty `mcp.allow/deny`/`departments` and `tools.web: true`: **confirmed verbatim** (read the file directly).
- `office.config.local.json`'s `mcp.departments` keys: the plan (lines 24, 127-131, Task 6b) asserts these are "stale," keyed to pre-redesign names like `content`/`secdata` that "don't match the current 8-department roster." Reading the actual file: `mcp.departments` keys are `engineering, frontend, devops, revenue, secdata, fin, slack(→exec...content), gmail(→content, revenue...)` — **every key already matches the current roster exactly** (`content` and `secdata` are the current, not stale, department ids). Task 6b as written would have someone "fix" a config file that is not broken, by rewriting its already-correct keys to `success`/`product`, which do not exist — that would actively break Task 2's runtime policy gate, not fix it. This is the plan's single highest-risk defect: Task 2 depends on Task 6b (line 80), and Task 6b's action item is pointed at the wrong target.
- The plan is internally aware of the real department names: the Application audit section (line 32) directly quotes the live check output saying *"Content, Finance and Revenue"* — confirmed this exact string still appears when re-running `npm run check` (`server: a routine outside Emails, Accounting and Sales is refused with a sentence — Routines come to Engineering in a later release. This release: Content, Finance and Revenue.`). So the plan simultaneously states the real department names (in the audit section) and a different, nonexistent set (everywhere else) — an internal inconsistency, not just a stale fact.
- **Concrete recommendation (not a choice of two):** keep Task 6b, but repoint it. Its underlying goal — making sure `mcp.departments` tracks the real roster — is still legitimate work; the defect is only in its stated premise ("stale") and its target department names. Reword Task 6b to (a) state the real current department set (`exec, revenue, engineering, frontend, devops, secdata, fin, content`) instead of `success`/`product`, (b) note that `office.config.local.json` is *already correct* against that real set and needs no edit today, and (c) make Task 6b's actual deliverable the rename-tracking contract: if/when the owner later renames `secdata`→`success` and `content`→`product` as part of the org redesign, Task 6b is the task that updates `mcp.departments` (and nothing else needs to change in Task 2, which only reads whatever `mcp.departments` says). This keeps Task 2's dependency on Task 6b meaningful without requiring an immediate, incorrect edit.
