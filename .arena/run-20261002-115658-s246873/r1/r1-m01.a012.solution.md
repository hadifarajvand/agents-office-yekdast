# Validation report: `agents-office-implementation.plan.md` vs. the repository

## Verdict up front

**Not safe to execute Task 1 onward as written.** The plan's own ground-truth premise about the current department structure is wrong in a way that invalidates a load-bearing claim repeated through the header, Task 2, Task 6b, and the entire 70-seat target table in Part II. The `npm run check` baseline the plan cites is also stale, and the check suite itself is flaky on this machine, so any single run's count should be reported as a range, not a fixed fact. Two of the plan's specific code-behavior claims (a 404-handler line citation, and what `applyRoster()` patches) are also wrong. Everything else checked below (file inventory, most specific line numbers, config contents, dependency state, and the UI collision arithmetic) holds up well — the plan was clearly written against the real codebase, just at an earlier moment and with a few uncorroborated claims that don't survive a direct read. The corrections below must land before anyone starts Task 1.

---

## Finding 1 (severe): the current department names are not what the plan says they are

The plan states, as a load-bearing fact repeated in multiple places:

- Header, line 12: *"Department names and count (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout."*
- "Current agent stack — ground truth" (line 18): *"`office.agents.json` has the 8-department structure applied (35 seats today...)"* — implying the `success`/`product` names are already live.

This is false against the repo as it stands. Independent sources in the codebase agree with each other and disagree with the plan:

- `backend/app/roster.py:31` (comment, verbatim, confirmed by `grep -n`): *"...matches routines.mjs's DEPT_KEYS (exec/revenue/engineering/frontend/devops/secdata/fin/content)."*
- `backend/app/mcp.py:16`: `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`
- `src/data.js` `LAYOUT`: keys are `brain, exec, revenue, engineering, frontend, devops, secdata, fin, content` — no `success`, no `product`.
- `office.agents.json` itself (35 agents): department counts are `content:3, devops:5, secdata:3, revenue:8, frontend:4, exec:3, fin:3, engineering:6` = 35. Again: `content` and `secdata`, not `success`/`product`.

So the real current 8 departments are `exec, revenue, engineering, frontend, devops, secdata, fin, content`. `success` and `product` do not exist anywhere in the code today. This is consistent with the repo's own git history — the most recent commit before this session is *"Backup: snapshot working tree before 8-department/80-seat Citadel redesign"* — i.e., the department rename to the new names has not happened yet; it's exactly the work this plan is supposed to schedule, not a fact already true.

This cascades into concrete errors elsewhere in the plan:

- **Task 6b is backwards.** The plan says `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, etc. — confirmed by direct read) are *"stale, pre-redesign keys that don't match the current 8-department roster."* They are not stale — `content` and `secdata` are exactly the current, live department ids used by `roster.py`, `mcp.py`, and `src/data.js` today. There is no bug here to fix as described. If the intent is that these keys should eventually become `success`/`product`, that only becomes true *after* a department-rename task that does not exist anywhere in this plan (and which `CLAUDE.md`'s own rule — "Fixed, and the office ignores edits to them: `id`, `department`, `lead`" — says cannot be done by editing a config file; it requires a code change to `roster_seed.json`/`DEPT_KEYS`/`src/data.js`, which this plan never schedules).
- **Task 2's connector matrix** assigns access to `success` and `product` — departments that don't exist in `office.config.local.json`'s actual roster. Shipped against the real repo, this table is unenforceable as written; it needs to be remapped to `content`/`secdata` (or wait on the rename this plan never schedules).
- **Part II's entire seat-cap table** (Leadership/`exec` 7, Product/`product` 6, Customer Support/`success` 5, etc.) targets two department ids, `product` and `success`, that are not in the roster, the seed, or the layout today. Either this table is a target for *after* an unscheduled rename task, or the plan needs an explicit Task 0 for the rename itself (touching `roster_seed.json`, `mcp.py:16`, `src/data.js`'s `LAYOUT`/`BILLBOARDS`/`APPROVAL_ASKS`, and `routines.mjs`'s `DEPT_KEYS`) before Task 10 onward can proceed against real department ids.
- **Task 11's "Decided" pilot department = `success`** is a decision about a department that doesn't exist yet. The decision may still stand once the (missing) rename task lands, but as stated it reads as already-actionable, and it isn't.

**Correction needed**: Rewrite the "ground truth" section and header to state the actual current 8 department ids (`exec, revenue, engineering, frontend, devops, secdata, fin, content`), add an explicit task (or fold into Task 6b) for renaming `secdata → success` and `content → product` (or whatever the owner actually wants `success`/`product` to map from) across `roster_seed.json`, `mcp.py:16`'s `DEPT_KEYS`, `src/data.js`'s `LAYOUT`/`BILLBOARDS`/`APPROVAL_ASKS`, and the Node `routines.mjs` equivalent — and sequence Task 6b, Task 2's connector matrix, and all of Part II's department-specific tasks after it.

## Finding 2 (severe): the `npm run check` baseline is stale, and the plan treats a flaky suite's output as a fixed number

The plan states (line 20 and line 30): *"`npm run check` passes 37/38 (one pre-existing, unrelated failure: `server: /api/brain has the live graph`...)."* and *"Everything else is green."*

That baseline is stale. But more importantly, running the suite repeatedly against the identical commit, with no code changes in between, produces **different results each time** — the suite is flaky, not deterministic, so no single run should be reported as "the" corrected number:

- Run 1: `34/38` — fails: `smoke: command bar adds a task in demo mode`, `smoke: department focus opens the chat rail`, `smoke: approval flow reaches the panel`, `server: /api/brain has the live graph`.
- Run 2: `35/38` — fails: `smoke: department focus opens the chat rail`, `smoke: approval flow reaches the panel`, `server: /api/brain has the live graph` (the command-bar failure did not recur).
- Run 3: `34/38` — same four failures as Run 1.

Across three consecutive runs, `server: /api/brain has the live graph` failed every time — that's the one stable, reproducible failure (and the only one the plan already names). The other three (`command bar adds a task in demo mode`, `department focus opens the chat rail`, `approval flow reaches the panel`) are intermittent — almost certainly browser-timing/Playwright flakiness in the smoke suite, not a fixed defect count. The plan's claim that "everything else is green" is still wrong (there are reproducible failures beyond the brain-graph one), but the correction is not a single fixed number — it's "this suite is not currently green, and its own smoke tests appear timing-flaky; at minimum the brain-graph failure is a stable, confirmed regression against the plan's claim, and the command-bar/department-focus/approval-flow checks fail intermittently and need triage for flakiness before being counted as new defects."

(One thing the plan gets right in the same section: the drift between `CLAUDE.md`'s routine-gating wording — "Emails, Accounting and Sales" — and the live check's own wording is real; the current check output literally says *"Routines come to Engineering in a later release. This release: Content, Finance and Revenue"* — note it also uses `Content`, reinforcing Finding 1.)

**Correction needed**: Replace "37/38... one failure" with: "currently 34-35/38 across repeated runs; `server: /api/brain has the live graph` fails on every run and is a confirmed, reproducible gap from the plan's claim; the three smoke-suite failures are intermittent and must be triaged for test flakiness (not assumed to be real regressions, and not assumed to be absent) before Task 7's contract-test work begins." Do not bake a single run's count into the plan as a fixed baseline.

## Finding 3 (moderate): two of the plan's own code-behavior citations are wrong

- **404-handler line citation is wrong.** The plan's API contract table (line 160) claims `main.py:454-456` is the catch-all `404 {"error":"not found"}` handler. Direct read of `backend/app/main.py:453-456` shows this is actually `@app.exception_handler(Exception)` / `on_error`, which returns a generic `500` for any unhandled exception — not a 404 route at all. The real per-route 404 returns (`JSONResponse({"error": "not found"}, status_code=404)`) are at `main.py:201`, `321`, and `350`. A reader following the plan's table literally would write a wrong assertion for the "catch-all route" in Task 7's contract tests.
- **`applyRoster()` does not patch `tools`.** The plan (Task 9b) asserts `applyRoster()` "already live-patches name/role/does/tools for any agent id present in both the server's live roster and the frontend's static `src/data.js` fallback." Direct read of `src/main.js:1331-1344` shows the function sets only `r.a.name`, `r.pill.innerHTML`, `r.v1.role`, `r.v1.tagline`, `r.v1.greeting`, and `r.v1.chips` — there is no `tools` field written anywhere in its body. This weakens Task 9b's stated rationale: whatever gap Task 9b is meant to close, "tools" is not already live-patched today and needs its own fix, not just confirmation.

**Correction needed**: Fix the `main.py:454-456` citation in the contract table to point at the actual 404 sites (`main.py:201, 321, 350`) and describe line 453-456 correctly as the generic exception handler. Revise Task 9b's rationale to state that `applyRoster()` currently patches name/role/tagline/greeting/chips only, and that live-patching `tools` is new work, not already-existing behavior.

## Finding 4 (moderate): Task 7 / `test_api_contract.py` is listed as CREATE but already exists and is largely done

The plan's own "ground truth" section lists `test_api_contract.py` as one of the 6 test files **already present** in `backend/tests/`. But the "Files to Change" table lists it as `CREATE | One test per route...; highest priority`, and Task 7's description frames writing these tests as not-yet-done, highest-priority work.

Direct read of the file: it exists today at 310 lines with 27 test functions (`test_health_shape`, `test_agents_shape`, `test_skills_shape`, `test_lessons_shape`, `test_mcp_shape`, `test_brain_shape`, `test_usage_shape`, `test_list_tasks_empty`, `test_create_task_requires_dept_and_text`, `test_create_task_routes_and_persists`, `test_run_blocks_and_returns_completed_task`, `test_revise_blocks_and_returns_completed_task`, `test_run_unknown_task_404`, `test_approve_acks_immediately_before_background_work_finishes`, `test_approve_requires_waiting_state`, `test_reject_acks_immediately`, `test_delete_task`, `test_list_routines_shape`, `test_create_routine_rejects_unknown_dept`, `test_create_routine_rejects_non_routine_department`, `test_create_routine_requires_text`, `test_create_routine_requires_a_resolvable_schedule`, `test_create_run_pause_resume_patch_delete_routine_roundtrip`, `test_patch_unknown_routine_404`, `test_chat_requires_known_agent`, `test_chat_returns_reply`, `test_unknown_route_404`). This maps essentially 1:1 onto the plan's own contract table, including the blocking-vs-async-ack distinction the plan specifically calls out as something to assert.

**Correction needed**: Change the Files-to-Change action for `test_api_contract.py` from `CREATE` to `UPDATE` (or drop it from the table), and reframe Task 7 as "confirm/extend existing coverage" rather than "write this first" — the highest-value remaining work in that group is likely confirming no route/shape is missing a test (including fixing the wrong 404-handler citation from Finding 3), not building the suite from scratch.
