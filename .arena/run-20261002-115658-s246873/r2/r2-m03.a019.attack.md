ATTACK 1 [MAJOR] Misreads the structure of office.config.local.json's mcp.departments, the exact file Task 6b turns on
Where: a016 solution, "Consequences that cascade" item 1: "Reading the file directly: every key in it (`content`, `secdata`, `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`) is a **valid, currently-live department** per `office.agents.json`."
Problem: This is a factual misdescription of the file. The actual `mcp.departments` object in `office.config.local.json` is keyed by connector name (`github`, `gitlab`, `slack`, `gmail`, `notion`, `docker`, `prometheus`, `grafana`), each mapping to an array of department ids. `content`/`secdata`/`exec`/etc. are array *values* nested under those connector keys, not the object's keys. A reader who takes a016's sentence at face value and goes to check "the keys" against the roster, as the task instructs ("open the actual file... and confirm whether it is true today"), will be looking at the wrong level of the JSON and cannot verify the claim as stated. The substantive conclusion (the department ids referenced happen to be live) survives, but the report describes a file structure that does not exist, which is exactly the kind of unverifiable, unactionable description category 4 of the task ("VAGUE... user could not act on it without guessing") warns against — except here it's worse than vague, it's simply wrong about what a "key" is in this JSON.

ATTACK 2 [MAJOR] Finding #5 (Task 16 layout arithmetic) explicitly ducks the sanity-check the task requires
Where: a016 solution, finding #5: "The ~10-unit-margin → ~4.8-unit-margin shrink is arithmetically plausible given a ~10-unit depth increase to ~38.4 split across both neighbor sides; the plan already flags this as needing re-verification against real ring-neighbor geometry before Task 17, and that caveat should stay."
Problem: Task requirement 8 explicitly says: "sanity-check the arithmetic the plan presents (margin shrinking from ~10 to ~4.8 units) rather than taking it on faith." a016 does not compute the margin — it has `src/data.js`'s real `LAYOUT` values in hand (`engineering: pos:[46,12], d:28`; `devops: pos:[-12,56], d:26`; `frontend: pos:[30,48], d:24` is also in the same file) and could have worked the actual ring-neighbor distance minus summed half-depths, the same way the task demands. Instead it asserts the shrink is "plausible" and defers to the plan's own caveat — which is restating the plan's claim back as if independently verified, the exact anti-pattern the task's "What NOT to do" section forbids ("Do not just restate the plan's own text back as if it were your own verification — you must actually open the cited files and compare"). The arithmetic was checkable (position deltas and depths are right there in the file a016 itself quotes) and a016 chose not to do it.
