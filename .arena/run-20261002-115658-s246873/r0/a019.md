## 1. The load-bearing claim that breaks the most things: department names

The plan states, twice, in load-bearing language:

> "Department *names* and *count* (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout." (line 12)
> "`office.agents.json` has the 8-department structure applied (35 seats today...)" (line 20)

**This is false.** I read `office.agents.json`, `src/data.js`, and `backend/app/mcp.py`'s own `DEPT_KEYS` constant — all three agree the current 8 departments are:

```
exec, revenue, engineering, frontend, devops, secdata, fin, content
```

`secdata` and `content` appear nowhere being replaced by `success`/`product`. I grepped the entire repo (`.json/.js/.py`, excluding `graphify-out`/`.arena`) for `"success"` and `"product"` as department-like tokens: **zero hits**. `success` and `product` are not current department keys anywhere in the code — they only exist in Part II's *target* table (line 236-246) as names for what Task 17 will eventually rename `secdata`→`success` ("Customer Support") and... actually the plan never states which current department becomes `product` either (`content`? `secdata`? neither obviously maps to "Product"). Either way, Part I's "ground truth" section presents a rename that has **not happened yet** as an accomplished fact, then reuses those department ids as if they're real throughout Tasks 2, 6, and 6b.

Knock-on effects:
- **Task 6b is built on a false premise.** It says `office.config.local.json`'s `mcp.departments` keys are "stale" because they use `content`/`secdata` instead of the current 8-dept set. I read the file directly — its keys (`github`, `gitlab`, `slack`, `gmail`, `notion`, `docker`, `prometheus`, `grafana`) are wired to exactly `exec/revenue/engineering/frontend/devops/secdata/fin/content`, which is precisely the **actual** current department set. `office.config.local.json` is not stale against today's roster — it's internally consistent with it. The real gap is the opposite direction: it has no entries yet for whatever `success`/`product` *become* once Task 17 renames things.
- **Task 2's connector matrix** (line 83-93) is written entirely in terms of `revenue, engineering, devops, fin, product, success` — a department set that doesn't exist in the roster yet. Anyone implementing Task 2 today cannot "remap to the current 8-dept roster" as instructed, because the current roster uses `secdata`/`content`, not `success`/`product`.
- **Task 11's pilot department is "`success`" (line 300)**, chosen because it's a 5-seat cap in the *target* table. But there is no `success` department today — the closest current 5-seat department is `devops`. The plan never says which existing department (or existing seats) becomes the pilot's `success` roster, or when the rename happens relative to Task 17 (full rollout) — which is supposed to be *later* than the pilot. This is a genuine sequencing gap, not just a naming nit: Task 11 is scheduled before Task 17, yet it requires a department key that (per the plan's own Task 17 description) only comes into existence *during* Task 17.

Separately, the repo's own `.claude/LANGGRAPH-MIGRATION-PLAN.md:177` still describes "the 35-seat/6-department fixed structure from `CLAUDE.md`" (six departments: `emails/sales/marketing/ops/fin/delivery` — see the project `CLAUDE.md`). That's a *third*, different department scheme, neither the plan's 8-dept claim nor the real current 8-dept roster. The plan doesn't address this discrepancy at all, even though it cites `LANGGRAPH-MIGRATION-PLAN.md` as a source.

**Correction needed**: Rewrite the "Current agent stack — ground truth" section and every subsequent department-name reference in Part I to say the real current set (`secdata`, `content`, not `success`/`product`), and have Task 6b state its actual finding correctly: `office.config.local.json` already matches the current roster; what's missing is forward-looking wiring for the *renamed* departments Task 17 will introduce. Task 11 needs an explicit statement of which existing department/seats become the pilot's `success` roster before Task 17 runs.

## 3. The "Verified API contract" table (Task 7) has two wrong rows

The plan claims this table is "confirmed matching `src/tasks.js`/`src/connectors.js`/`src/main.js` exactly" (line 137) and cites file:line for each row. Two rows are wrong:

- **`POST /api/chat` → `main.py:423-452`**: the plan claims the response shape is `{reply, read, tools, used, interview, routine?, routines?, setup?}`. I read `main.py:423-451` directly — every code path in `chat()` returns either `{"reply": routines_mod.list_text(...)}`, `{"reply": f'Done — ...'}`, or `{"reply": reply}` from `engine.chat(...)`. There is no `read`, `tools`, `used`, `interview`, `routines`, or `setup` key anywhere in this function. The claimed response shape does not match the actual code at all.
- **`* anything else → 404 {error:'not found'}` → `main.py:454-456`**: lines 454-456 are `@app.exception_handler(Exception) async def on_error(...)`, a **generic 500 handler** (`return JSONResponse({"error": str(exc)}, status_code=500)`), not a catch-all 404 route. FastAPI's default behavior for unmatched routes is its own 404, which this code doesn't customize at all — there is no explicit `{error: 'not found'}` 404 handler in `main.py` at the cited lines or anywhere else I could find.

Every other row in the table (health, agents, skills, lessons, mcp, brain, usage, tasks GET/POST, routines GET/POST/run/pause/resume/patch/delete, run/revise blocking vs. approve/reject async-ack) I checked line-by-line against the actual file and they are accurate, including the blocking-vs-async split the plan calls out specifically (`main.py:190-216` blocks; `main.py:219-260` acks immediately via `asyncio.create_task`).

**Correction needed**: Fix the `/api/chat` row to reflect the real `{"reply": ...}`-only shape, and fix the catch-all row to describe the actual generic exception handler (500, not 404) — or note explicitly that FastAPI's default 404 is unverified/unexercised by this table.
