# Validation report: `agents-office-implementation.plan.md` vs. the current repository

## Headline finding (overrides most of the plan's "ground truth" section)

The plan's foundational claim — "`office.agents.json` has the 8-department structure applied... Department *names* and *count* (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout" (plan lines 12, 18-20) — **is false against the repo as it stands right now.**

`office.agents.json` today has 35 agents across 8 departments, but the actual keys are:

```
exec: 3, revenue: 8, engineering: 6, frontend: 4, devops: 5, secdata: 3, fin: 3, content: 3
```
(verified by loading the JSON and counting — `office.agents.json`)

That is `content` and `secdata`, not `success` and `product`. These are exactly the same keys the plan calls "pre-redesign" and claims are stale only in `office.config.local.json`'s `mcp.departments` (plan line 24, Task 6b). They are not stale leftovers in a side config — they are the live department identity of every agent in the roster, baked into `backend/app/mcp.py`'s own `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]` (mcp.py line ~15), into `src/data.js`'s `LAYOUT`/`BILLBOARDS`/`APPROVAL_ASKS` maps (data.js lines 80-116, all keyed `secdata`/`content`), and into `backend/app/routines.py` (`NAMES = {"content": "Content", "fin": "Finance", "revenue": "Revenue", "exec": "Exec", "engineering": "Engineering", "frontend": "Frontend", "devops": "Devops", "secdata": "Secdata"}`, routines.py line 17).

The strings `success` and `product` do not appear as department keys anywhere in `office.agents.json`, `backend/app/mcp.py`, `backend/app/routines.py`, or `src/data.js`. Confirms it further: the most recent commit before this plan was written is literally titled **"Backup: snapshot working tree before 8-department/80-seat Citadel redesign"** (`git log`, commit `92de5bd`, 2026-10-02 03:18). That commit message, by its own wording, documents that the `exec/revenue/engineering/frontend/devops/fin/success/product` 8-department target the plan treats as *already live* is the thing that redesign has **not yet executed** — the repo is still on the pre-redesign department scheme (`content`/`secdata` instead of `product`/`success`... and note even that mapping is not 1:1: there is no current department corresponding cleanly to `product`, and `secdata` has no obvious successor named in the plan at all).

**Consequence**: every downstream claim in the plan that depends on "the current 8-department roster" being `exec/revenue/engineering/frontend/devops/fin/success/product` is built on a false premise — most importantly Task 6b (which is solving a problem that doesn't exist the way it's described) and the entire "Current department/seat-count target" table in Part II. See the detailed breakdown below.

## 2. Structural/roster claims — the 35→70 target

- **35-seat baseline**: confirmed. 35 agents in `office.agents.json` today.
- **"8 departments" baseline**: technically confirmed as a *count* (8 department keys exist) but **the named set is wrong** — see Headline finding. The actual 8 are `exec, revenue, engineering, frontend, devops, secdata, fin, content`, not `exec, revenue, engineering, frontend, devops, fin, success, product`.
- **70-seat target table** (Leadership 7, Sales & Marketing 13, Product 6, Backend Engineering 14, Frontend Engineering 6, Infrastructure & QA 14, Customer Support 5, Finance 5 = 70): this is a forward-looking target, not a claim about current repo state, so it isn't "wrong" on its own terms — but it's built entirely on the false premise that `product` and `success` already exist as department identities today. They don't. Two of the plan's eight target departments (`product`, `success`) have **no current department to rename from** — `secdata` and `content` are the two departments that would need renaming/repurposing, and the plan never says so. This is a real gap: Task 17 (full rollout) and Task 11 (pilot, decided as `success`) both assume `success` is a live department key today that merely needs more seats added. It isn't. Someone executing Task 11 as written would look for a `success` department in `office.agents.json`, find none, and be blocked immediately — a renaming/repurposing step (`secdata`→? or `content`→`success`? unclear which) is a prerequisite the plan never states.
- `office.agents.local.json` does not exist yet: **confirmed** (`ls` returns "No such file or directory").
