## Headline finding (affects categories 2, 4, 6, and the plan's own framing)

**The plan's central premise about the current department scheme is wrong.** The plan states, in its header and repeatedly thereafter, that the current 8 departments are `exec, revenue, engineering, frontend, devops, fin, success, product`, and that `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, etc.) are "stale, pre-redesign" keys that need remapping to this scheme.

This is backwards. The actual current department set, confirmed independently in three places, is **`exec, revenue, engineering, frontend, devops, secdata, fin, content`** — there is no `success` or `product` department anywhere in the live repo:

- `office.agents.json` (35 agents): `Counter({'revenue': 8, 'engineering': 6, 'devops': 5, 'frontend': 4, 'content': 3, 'secdata': 3, 'exec': 3, 'fin': 3})` — 8 departments, 35 seats, and they are `content`/`secdata`, not `success`/`product`.
- `backend/app/mcp.py:16`: `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]` — hardcoded in the policy module itself.
- `src/data.js:17-28`: `export const DEPT_KEYS = ['exec', 'revenue', 'engineering', 'frontend', 'devops', 'secdata', 'fin', 'content'];` plus full `DEPTS` display names (`SECURITY & DATA`, `CONTENT & COMMS`, etc.), with a dated comment: "V4 (1 Oct 2026): full structural redesign — the office moved from a 6-pod go-to-market/ops shape to an 8-pod build-and-run shape... Operations split into EXEC..., ENGINEERING, FRONTEND, DEVOPS and SECDATA. Emails folded into CONTENT."

A repo-wide grep for `"success"`/`"product"` as department identifiers across `office.agents.json`, both config files, `src/data.js`, and `backend/app/*.py` returns zero hits. The 8-department, 35-seat redesign the plan treats as historical baseline ("current") is not the one that shipped — a *different* 8-department redesign (the `secdata`/`content` one) is what's actually in the tree, dated 1 Oct 2026, one day before the plan's own "2026-10-02" status line.

**Consequences for the plan as written:**
- Task 6b is solving the wrong problem. `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, `revenue`, `engineering`, `devops`, `fin`, `exec` — confirmed by reading the file directly) are **not stale** — they match the live roster and the live `mcp.py`/`data.js` department sets exactly. If Task 6b is executed as specified ("rewrite each to its corresponding current department name," i.e., swap `content`→ something and `secdata`→ something involving `success`/`product`), it would break a config file that currently resolves correctly against every other part of the system.
- Task 2's connector matrix (the table under "Connector matrix to implement against") is keyed to `revenue, engineering, devops, fin, success, product` — two of those six values don't exist as departments. The matrix needs to be rebuilt against the real 8 (`exec, revenue, engineering, frontend, devops, secdata, fin, content`) before it's usable as an acceptance target.
- Task 6's "Note (department remap)" instruction ("re-derive their current department from the current 8-dept table, e.g. an agent that was `sales` is now `revenue`") is premised on the same wrong target set.
- Part II's whole target table (Leadership/Sales & Marketing/Product/Backend Engineering/Frontend Engineering/Infrastructure & QA/Customer Support/Finance, mapped to `exec/revenue/product/engineering/frontend/devops/success/fin`) assumes the current roster already has `product` and `success` seats to expand from. It doesn't — it has `content` and `secdata` seats instead, which aren't mentioned anywhere in Part II. Someone executing Task 17 would have no instruction for what happens to the current `content` (3 seats: comms/email) and `secdata` (3 seats: security/data) departments under the new 8-department target, since those department names simply vanish from the plan's vocabulary.

This is not a cosmetic naming quibble — it is the single fact the plan repeatedly calls "load-bearing," and it does not match the repository.
