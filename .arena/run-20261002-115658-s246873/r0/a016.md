## Headline finding: the plan's department scheme does not match the roster on disk

The plan states repeatedly (merge note, "Current agent stack" section, "Department remap" acceptance line) that `office.agents.json` already has an 8-department structure of **`exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`** — 35 seats, that scheme.

That is false. The actual departments in `office.agents.json` today are:

```
content: 3, devops: 5, secdata: 3, revenue: 8, frontend: 4, exec: 3, fin: 3, engineering: 6   (35 total)
```

`success` and `product` do not exist anywhere in the roster. `content` and `secdata` do exist and are exactly the kind of "pre-redesign" names the plan says it's correcting *away from* — except they're not legacy debris, they're the live department keys. `src/data.js`'s `AGENTS` array (the frontend fallback roster) matches this same scheme exactly, department-for-department and count-for-count (`content:3, devops:5, secdata:3, revenue:8, frontend:4, exec:3, fin:3, engineering:6` = 35) — so the frontend and backend roster are in sync with each other, just not with what the plan calls "current."

This is corroborated by the git log: the most recent commit (`92de5bd`, newer than the "Phase 1: unused-seats" and "v3.6.1-beta.1" commits) is literally titled *"Backup: snapshot working tree before 8-department/80-seat Citadel redesign"* — i.e., the repo is sitting at the pre-redesign snapshot, and the Citadel/8-dept/70-seat work the plan describes as a forward-looking Part II hasn't started touching the roster yet. `.claude/unused-seats.md` and `CLAUDE.md`'s "Department keys" section describe a *third*, even older scheme (`emails/sales/marketing/ops/fin/delivery`, 6 departments) — so there are three generations of department naming floating around the repo's own docs, and the plan's "current" baseline matches none of them; it matches the *target* state two generations ahead of what's on disk.

Consequences that cascade from this:

1. **Task 6b is solving the wrong problem.** The plan says `office.config.local.json`'s `mcp.departments` keys are stale because they're keyed to `content`/`secdata` instead of the current roster. I read the file directly:
   ```
   "github": ["engineering","frontend","devops"], "gitlab": [...,"secdata","fin"], "slack": [...,"secdata","fin","content"], "gmail": ["content","revenue"], ...
   ```
   Every key in there (`content`, `secdata`, `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`) is a **valid, currently-live department** per `office.agents.json`. This file is not stale — it is the one artifact in the repo that's already correctly wired to the real roster. Task 6b as written would have someone "fix" a config file that isn't broken, by renaming keys to departments (`success`, `product`) that don't exist yet.
2. **Task 2's connector matrix table** (`GitHub → revenue, engineering`, `Gmail → revenue, success`, etc.) is captioned "remapped to the current 8-dept roster" — it isn't; it's remapped to the *Part II target* roster. `success` doesn't exist to grant Gmail access to yet.
3. **The "Department remap" line in Foundation Acceptance** ("matches the current 8-department roster, not the stale 6-department one") sets up a false binary — the live roster is neither the 6-dept scheme nor the plan's assumed 8-dept scheme; it's a third, distinct 8-dept scheme the plan never names.

**What to fix in the plan**: replace every "current department structure is `exec/revenue/engineering/frontend/devops/fin/success/product`" claim with the actual live set (`content/devops/secdata/revenue/frontend/exec/fin/engineering`), drop or substantially rewrite Task 6b (the config file it targets is already correct), and make explicit in Part II that the `content→?` and `secdata→?` renames to `success`/`product`-equivalents are themselves part of the Task 17 rollout work, not an already-done precondition.

## Stale/false claims beyond the department scheme

1. **The 404 contract-table row is wrong.** The plan's API contract table says: `* | anything else | 404 {error:'not found'} | main.py:454-456`. Lines 454–456 are actually:
   ```python
   @app.exception_handler(Exception)
   async def on_error(_req, exc: Exception):
       return JSONResponse({"error": str(exc)}, status_code=500)
   ```
   That's a generic 500 handler for unhandled exceptions, not a 404-for-unmatched-routes handler. There is no explicit catch-all in `main.py` that returns `{"error":"not found"}` with status 404 for an arbitrary unmatched path — FastAPI/Starlette's own default 404 (`{"detail":"Not Found"}`) would fire instead for a genuinely unmatched route. The `{"error":"not found"}`/404 pattern does appear elsewhere (lines 201, 321, 350) but those are all for a *missing resource by id* within an existing route (task/routine not found), not a wildcard route. The contract table's final row should cite the exception handler correctly (500, not 404) or be dropped.
