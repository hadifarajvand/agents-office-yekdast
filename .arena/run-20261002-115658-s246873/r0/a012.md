# Validation report: `agents-office-implementation.plan.md` vs. the repository

## Verdict up front

**Not safe to execute Task 1 onward as written.** The plan's own ground-truth premise about the current department structure is wrong in a way that invalidates a load-bearing claim repeated through the header, Task 2, Task 6b, and the entire 70-seat target table in Part II. A second, independently verifiable claim — the `npm run check` baseline — is also stale (it understates the number of failing checks by 3x). Everything else checked below (file inventory, specific line numbers, config contents, dependency state, and even the UI collision arithmetic) holds up well; the plan was clearly written against the real codebase, just at a slightly earlier/different moment than "now." The two corrections below must land before anyone starts Task 1.

---

## Finding 1 (severe): the current department names are not what the plan says they are

The plan states, as a load-bearing fact repeated in multiple places:

- Header, line 12: *"Department names and count (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout."*
- "Current agent stack — ground truth" (line 18): *"`office.agents.json` has the 8-department structure applied (35 seats today...)"* — implying the `success`/`product` names are already live.

This is false against the repo as it stands. Three independent sources in the codebase agree with each other and disagree with the plan:

- `backend/app/roster.py:32` (comment, verbatim): *"...matches routines.mjs's DEPT_KEYS (exec/revenue/engineering/frontend/devops/secdata/fin/content)."*
- `backend/app/mcp.py:16`: `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`
- `src/data.js:80-90` (`LAYOUT`): keys are `brain, exec, revenue, engineering, frontend, devops, secdata, fin, content` — no `success`, no `product`.
- `office.agents.json` itself (35 agents, confirmed by `node` inspection): department counts are `content:3, devops:5, secdata:3, revenue:8, frontend:4, exec:3, fin:3, engineering:6` = 35. Again: `content` and `secdata`, not `success`/`product`.

So the real current 8 departments are `exec, revenue, engineering, frontend, devops, secdata, fin, content`. `success` and `product` do not exist anywhere in the code today. This is consistent with the repo's own git history — the most recent commit before this session is *"Backup: snapshot working tree before 8-department/80-seat Citadel redesign"* — i.e., the department rename to the new names has not happened yet; it's exactly the work this plan is supposed to schedule, not a fact already true.

This cascades into concrete errors elsewhere in the plan:

- **Task 6b is backwards.** The plan says `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, etc. — see `office.config.local.json`, confirmed by direct read) are *"stale, pre-redesign keys that don't match the current 8-department roster."* They are not stale — `content` and `secdata` are exactly the current, live department ids used by `roster.py`, `mcp.py`, and `src/data.js` today. There is no bug here to fix as described. If the intent is that these keys should eventually become `success`/`product`, that only becomes true *after* a department-rename task that does not exist anywhere in this plan (and which `CLAUDE.md`'s own rule — "Fixed, and the office ignores edits to them: `id`, `department`, `lead`" — says cannot be done by editing a config file; it requires a code change to `roster_seed.json`/`DEPT_KEYS`/`src/data.js`, which this plan never schedules).
- **Task 2's connector matrix** (lines 85-93) assigns access to `success` and `product` — departments that don't exist in `office.config.local.json`'s actual roster. Shipped against the real repo, this table is unenforceable as written; it needs to be remapped to `content`/`secdata` (or wait on the rename this plan never schedules).
- **Part II's entire seat-cap table** (lines 236-246: Leadership/`exec` 7, Product/`product` 6, Customer Support/`success` 5, etc.) targets two department ids, `product` and `success`, that are not in the roster, the seed, or the layout today. Either this table is a target for *after* an unscheduled rename task, or the plan needs an explicit Task 0 for the rename itself (touching `roster_seed.json`, `mcp.py:16`, `src/data.js`'s `LAYOUT`/`BILLBOARDS`/`APPROVAL_ASKS`, and `routines.mjs`'s `DEPT_KEYS`) before Task 10 onward can proceed against real department ids.
- **Task 11's "Decided" pilot department = `success`** is a decision about a department that doesn't exist yet. The decision may still stand once the (missing) rename task lands, but as stated it reads as already-actionable, and it isn't.

**Correction needed**: Rewrite the "ground truth" section and header to state the actual current 8 department ids (`exec, revenue, engineering, frontend, devops, secdata, fin, content`), add an explicit task (or fold into Task 6b) for renaming `secdata → success` and `content → product` (or whatever the owner actually wants `success`/`product` to map from) across `roster_seed.json`, `mcp.py:16`'s `DEPT_KEYS`, `src/data.js`'s `LAYOUT`/`BILLBOARDS`/`APPROVAL_ASKS`, and the Node `routines.mjs` equivalent — and sequence Task 6b, Task 2's connector matrix, and all of Part II's department-specific tasks after it.
