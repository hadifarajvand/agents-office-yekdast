### Stale / inconsistent / false — this is the plan's central, load-bearing defect

**The plan's department-name claim is factually wrong against the current repo, in both directions it needs to be right.**

The plan states (header, lines 12 and repeated at line 211, 234-248, 252, 300, etc.): *"Department names and count (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout."* It further asserts (lines 20, 24, 127-131) that `office.config.local.json`'s `mcp.departments` keys — `content`, `secdata`, etc. — are **stale, pre-redesign department names that don't match the current roster**, and builds Task 6b around rewriting them to the `exec/revenue/engineering/frontend/devops/fin/success/product` set.

This is backwards. Checking the actual code:
- `backend/app/mcp.py:16`: `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`.
- `backend/app/roster.py:31` (comment): *"...so this matches routines.mjs's DEPT_KEYS (exec/revenue/engineering/frontend/devops/secdata/fin/content)."*
- `office.agents.json`'s 35 agents break down by department as: `revenue:8, engineering:6, devops:5, frontend:4, content:3, secdata:3, exec:3, fin:3` (verified by direct count) — `content` and `secdata` are real, populated departments today; `success` and `product` do not exist anywhere in the roster, `mcp.py`, or `src/data.js`.
- `src/data.js`'s `LAYOUT` and `BILLBOARDS` tables are keyed by the same 8 names: `exec, revenue, engineering, frontend, devops, secdata, fin, content` — again, `success`/`product` appear nowhere.
- `npm run check`'s own smoke output confirms "eight department cards" against this same `content`/`secdata`-bearing roster.

So: `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, plus `exec/revenue/engineering/frontend/devops/fin`) are **exactly the current department set**, not a stale pre-redesign one. There is no confirmed bug here for Task 6b to fix as described. What actually doesn't exist anywhere in the current repo is `success` and `product` — those are *target* names for the 70-seat Org Redesign (Part II), not the *current* 8 departments the plan's Foundation section (Part I) claims they already are. The plan has conflated its own target-state naming with the current-state naming and then, on that false premise, invented a "fix" for a config file that was actually correct. This affects:
- Task 6b in full (the "fix" would break a currently-correct file by renaming `content`→`success`/`secdata`→`product`, before any seat in those departments has actually been renamed).
- Task 2's connector matrix table (lines 83-93), which is written against `exec/revenue/engineering/frontend/devops/fin/success/product` — it needs to be rewritten against the real current keys (`content`, `secdata`) for it to be enforceable today, and re-derived again once Task 17 actually renames departments.
- Task 6's "Note (department remap)" (line 123), which tells the implementer to "re-derive [AGENTS.md's 12 agents'] current department from the current 8-dept table (e.g. an agent that was `sales` is now `revenue`)" — `sales` isn't even in the picture; `.claude/AGENTS.md`/`.claude/unused-seats.md` actually describe a **third, older 6-department scheme** (`emails, sales, marketing, ops, fin, delivery`, 35 seats — this is also what the project's own `CLAUDE.md` describes), which matches neither the plan's claimed current 8-dept set nor the actual current 8-dept set in code. ## Overall verdict

**Not yet reliable as a basis to start Task 1 onward right now, specifically because of the department-naming defect — everything else is solid.**

The plan's backend code citations (file paths, line ranges, function names) are consistently accurate — this is not a plan that was never checked against the repo; it reads like careful, specific auditing for every Python/JS citation. The one load-bearing claim that is actually wrong is the department-naming premise that Part I's header asserts as "current," which cascades into Task 6b (fixing a file that isn't broken), Task 2's connector matrix (written against names that don't exist yet), and Task 6's remap note (understating how many generations of drift actually exist). The `npm run check` pass count is also now stale (33/38, not 37/38) with four new, unexplained smoke failures.

1. **Plan header (line 12) and every place that repeats "current" department names as `exec/revenue/engineering/frontend/devops/fin/success/product`**: split into "current" (`exec, revenue, engineering, frontend, devops, fin, secdata, content`, confirmed in `mcp.py:16`, `roster.py:31`, `office.agents.json`, `src/data.js`) vs. "target, from Task 17 onward" (`exec, revenue, engineering, frontend, devops, fin, success, product`). State explicitly that `secdata→product` and `content→success` (or whatever the real Task 17 mapping turns out to be) is a rename that has not happened yet.
2. **Task 6b**: re-scope. `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, etc.) are not stale — they match the current roster. Either drop Task 6b entirely from Part I (nothing to fix today) or reframe it as "add the startup-time department-key validator now, defer the actual rewrite to whenever Task 17 renames the departments for real."
3. **Task 2's connector matrix (lines 83-93)**: rewrite against the current 8 keys (`content`, `secdata` in place of `success`, `product`) so it's actually enforceable against `office.config.local.json` as it exists today; re-derive again post-Task 17.
4. **Task 6's remap note (line 123)**: correct "an agent that was `sales` is now `revenue`" — `sales` comes from a third, older 6-department scheme in `.claude/unused-seats.md`/root `CLAUDE.md` (`emails, sales, marketing, ops, fin, delivery`), not the current 8-department code. Flag that there are two hops of drift to reconcile (legacy 6-dept docs → current 8-dept code → this plan's target 8-dept names), not one.

Everything else in the plan — the Foundation task list, the risk table, the execution grouping, the Org Redesign's internal gating logic, the decided/open-item bookkeeping, and the UI collision-math caveats — holds up against the repo as written and does not need correction before someone starts on Task 1, 3, 4, 5, 7, 8, or 9.
