# Validation report: `agents-office-implementation.plan.md` vs. current repo

## Headline finding: the plan's "current department set" is wrong

The plan states, as a load-bearing fact repeated throughout (header, line 12; Task 2's connector matrix; Task 6b's whole rationale; Task 11's pilot pick): the office currently has 8 departments named `exec, revenue, engineering, frontend, devops, fin, success, product`.

That is false. The actual current department keys, confirmed in three independent places that must agree and do agree with each other:

- `office.agents.json` — the 35 agents are split `content: 3, devops: 5, secdata: 3, revenue: 8, frontend: 4, exec: 3, fin: 3, engineering: 6` (35 total, 8 departments).
- `src/data.js:17` — `export const DEPT_KEYS = ['exec', 'revenue', 'engineering', 'frontend', 'devops', 'secdata', 'fin', 'content']`.
- `office.config.local.json`'s `mcp.departments` keys — `engineering, frontend, devops, revenue, secdata, fin, content, exec` — i.e. they key against **the same department names as the live roster**.

So the real current 8 departments are `exec, revenue, engineering, frontend, devops, fin, secdata, content` — not `..., success, product`. `success` and `product` do not exist anywhere in the live roster, the frontend's department list, or the live connector config. They only appear as *target* department display-names in Part II's 70-seat table (`success` = Customer Support, `product` = Product).

This single error cascades into several of the plan's "confirmed" claims:

1. **Task 6b is built on an inverted premise.** The plan says `office.config.local.json`'s `mcp.departments` wiring is "stale," "keyed to an older department scheme (`content`, `secdata`...) that doesn't match the current 8-department roster" (lines 22, 24, 128). The opposite is true: `content`/`secdata` *are* the current roster's department keys (see `office.agents.json` counts and `src/data.js:17` above) — the config file is **correctly** wired against today's roster. There is no live-config drift to fix. What the plan is actually anticipating is that *after* Part II renames departments to `success`/`product` (etc.), this file will need updating — that's a real future task, but it isn't a "confirmed... real gap" today as Task 6b and the "Application audit" section claim, and Task 6b's described action ("rewrite each to its corresponding current department name") has nothing to rewrite yet because nothing is stale.
2. **Task 2's connector matrix table is unusable as written.** It lists `success` and `product` as department targets for Gmail and Notion access respectively. Neither department exists. Implementing Task 2 "against the current 8-dept roster" as instructed would have no `success`/`product` agents to grant access to.
3. **Task 11's pilot department choice needs translation.** "Pilot department is `success`" only makes sense once Part II's department rename has actually happened; today the nearest analog is `secdata` or there is no clean 1:1 mapping stated anywhere in the plan (the plan explicitly says the old→new department mapping is used "elsewhere in this plan" but never actually tabulates `content→?`, `secdata→?`; it only asserts the mapping exists).

**Correction needed**: Rewrite the "ground truth" sections (the header's department-name sentence, the "Current agent stack" section, Task 2's connector matrix headers, and Task 6b in full) to state plainly that the roster is still on `exec/revenue/engineering/frontend/devops/fin/secdata/content`, that `success`/`product`/etc. are Part II's *target* names only, and that the actual old→new department-name mapping needs to be written down somewhere in the plan before Task 6b, Task 2, or Task 10/11 can be executed against real data. As it stands, nobody could start Task 2 or Task 6b today without first reverse-engineering this mapping themselves.

## Overall verdict

**This plan is not a reliable basis to start Task 1 onward right now without corrections.** The specific, cited technical work in Part I (checkpointer, policy gate, redaction, contract tests, UI column math) is for the most part accurately grounded in the actual code — file paths and line numbers were independently checked against the real files and the overwhelming majority are correct, including a non-trivial arithmetic check (Task 16's margin math) that was reproduced from first principles and matches exactly. That is real, careful work, not guesswork.

But three corrections are needed before execution starts, in priority order:

1. **Fix the department-name premise (highest priority — affects Task 2, Task 6b, Task 10's dependency note, and Task 11).** Replace every claim that the current roster already uses `success`/`product`/etc. with the actual current names (`secdata`/`content`/etc., per `office.agents.json` and `src/data.js:17`). Rewrite Task 6b to state correctly that `office.config.local.json` is currently *consistent* with the live roster, not stale, and either (a) scope Task 6b as "write the old→new department mapping, to be applied once Part II actually renames departments" rather than "fix a drift that already exists," or (b) drop it until Part II's rename actually happens. Rewrite Task 2's connector matrix to use the real current department names so it's actually implementable against `office.agents.json` as it exists today.
2. **Re-run and update the `npm run check` baseline.** The plan's "37/38 passed, one unrelated failure" claim is stale; the real number today is 33/38 with four additional smoke-test failures the plan doesn't mention or account for in its risk analysis.
3. **Mark Task 7 as already complete**, not as a "do first" pending task — `test_api_contract.py` already exists, fully implements the described contract tests, and its docstring already cites this plan. Update the "Files to Change" table's `CREATE` to `(already exists)` and adjust the Execution-grouping table (Group A) accordingly.

Two smaller corrections: fix the false `main.py:454-456` → 404-catch-all citation (it's actually a 500 generic-exception handler), and resolve Task 10's heading gate ("Tasks 1, 2") against its own stated dependency on Task 6.

Everything else checked — the Foundation file/module inventory, the requirements.txt/docker-compose infrastructure claims, the decided-vs-open labeling, the Part I/II gating language, and the UI collision math — held up against direct inspection of the repository and can be trusted as-is.
