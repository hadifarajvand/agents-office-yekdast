# Validation Report: `agents-office-implementation.plan.md` vs. current repository

## Assumptions
- "Current state of the repository" means the working tree as it sits on `main` right now (verified via direct file reads, `npm run check`, and `git log`), not any branch the plan's author may have had checked out when writing it.
- Where the plan cites a line range and the actual boundary is off by 1–2 lines (e.g. a decorator line vs. the function body), I treat that as accurate and don't flag it as a discrepancy — only genuine mismatches are reported as findings.

## Headline finding (affects categories 2, 4, 6, 7, 9)

**The plan's department-name baseline is factually wrong.** The plan states, in its preamble and again in §"Current agent stack": *"Department names and count (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout."*

That is not what's on disk. The actual current department set, confirmed in three independent places that must agree with each other and do:
- `office.agents.json` — seat counts by dept: `content: 3, devops: 5, secdata: 3, revenue: 8, frontend: 4, exec: 3, fin: 3, engineering: 6` (35 total).
- `backend/app/mcp.py:16` — `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`.
- `src/data.js:17` — `DEPT_KEYS = ['exec', 'revenue', 'engineering', 'frontend', 'devops', 'secdata', 'fin', 'content']`, and its `LAYOUT` object (line 80) keys plinths the same way.
- `npm run check`'s own smoke output confirms "eight department cards" against this same 8-dept set.

So today's 8 departments are `exec, revenue, engineering, frontend, devops, secdata, fin, content` — **not** `exec, revenue, engineering, frontend, devops, fin, success, product`. `secdata` and `content` exist; `success` and `product` do not exist anywhere in the roster, the backend, or the frontend data layer. This also means the git history is informative here: the most recent commit is literally titled *"Backup: snapshot working tree before 8-department/80-seat Citadel redesign"* — i.e., the repo you're validating against is a pre-redesign snapshot. The plan was written as if the department rename to `success`/`product` had already landed; it hasn't.

Everything downstream that assumes `success` and `product` exist today inherits this error — see categories 2, 4, 6, 7, 9 below.

There is also a third, older scheme still present in checked-in docs: the project's own `CLAUDE.md` (repo root) and `.claude/unused-seats.md` describe a *different* 6-department, 35-seat baseline (`emails, sales, marketing, ops, fin, delivery`, caps 5/6/7/6/4/7) that matches neither the plan's claimed baseline nor what's actually in `office.agents.json` today. The plan doesn't mention this third scheme at all — worth flagging as "anything else materially wrong" (category 9), since whoever picks up Task 6/6b will hit three mutually inconsistent sources of truth (root `CLAUDE.md`, `office.agents.json`'s actual keys, and the plan's claimed keys), not two.

  1. Engineering's current depth is 28, devops's is 26 — **they are not the same today**, but the plan's collision math treats both 14-seat departments identically, growing both to "~38.4 units" depth and computing one single "~10 → ~4.8" margin figure as if it applies uniformly to both. Since the two departments start from different depths (26 vs 28) and presumably have different neighbor distances, a single shared margin number for both is an oversimplification the plan doesn't flag as such — it should either show the math per-department or explicitly say the 4.8 figure is illustrative/worst-case for one of the two, not both.
  2. I did not attempt to independently re-derive the "~10 units → ~4.8 units" neighbor-margin figure from the `LAYOUT` positions, because the isometric floor plan's actual plinth-to-plinth clearance depends on the ring arrangement's rotation and which axis ("depth") the margin is measured along — information not fully recoverable from `LAYOUT`'s flat `pos`/`w`/`d` alone without also reading the three.js scene-construction code that places plinths relative to each other. The plan itself acknowledges this is an estimate ("re-verified against the actual neighboring department's plinth geometry... not assumed safe by extrapolation alone") — that caveat is appropriate and should stay; I can confirm the inputs it worked from (28/26 depth, not a single shared value) are real, but not that 4.8 is the exact correct output.
- The plinth-width question Task 16 leaves open is, as the plan says, genuinely still open — I found no width-equivalent computation anywhere in `LAYOUT` or `main.js` that would have already answered it.

## Overall verdict

**This plan is not a reliable basis to start executing Task 1 onward right now, because its single most load-bearing factual claim — the current department names — is wrong**, and that error propagates into Task 2's connector matrix, Task 6/6b's entire premise, Task 11's pilot-department choice, and the 70-seat target table's department identifiers (categories 2, 4, 6, 7, 9 above). Everything else in the plan — every backend file:line citation, every API contract entry, the `npm run check` 37/38 result and its exact failure message, the dependency/infra claims, the frontend line citations, and the internal decided-vs-open bookkeeping — checked out as accurate on direct inspection. The plan is well-grounded in the parts that don't touch department identity; it is wrong in the parts that do.

**Concrete corrections needed before this plan is safe to execute:**

1. **Preamble + "Current agent stack" section**: replace the claimed current department set `exec, revenue, engineering, frontend, devops, fin, success, product` with the actual current set `exec, revenue, engineering, frontend, devops, secdata, fin, content`. State explicitly whether `secdata`→`success` and `content`→`product` are intended renames (and if so, when/where that rename happens — it isn't any existing task) or whether `success`/`product` are net-new departments that replace `secdata`/`content` outright, with a migration step for existing seats in those two departments.
2. **Task 6b**: rewrite its premise. `office.config.local.json`'s `mcp.departments` keys (`content`/`secdata`/etc.) are **not** stale relative to the current roster — they match it. The actual gap is that the plan's *own* target scheme (`success`/`product`) doesn't exist anywhere yet. Task 6b should become "decide and execute the `secdata`/`content` → `success`/`product` rename (if that's the decision) across `office.agents.json`, `mcp.py:16`'s `DEPT_KEYS`, `src/data.js:17`'s `DEPT_KEYS` and `LAYOUT`, and `office.config.local.json`'s `mcp.departments`, keeping all four in lockstep" — not "fix stale keys."
3. **Task 2's connector matrix**: its department column (`revenue, engineering, devops, fin, success, product`) needs the same correction once #1 above is decided — right now it's written against departments that don't exist in `mcp.py`'s `DEPT_KEYS`.
4. **Task 11 (pilot)**: "pilot department is `success`" is not actionable until #1 is resolved, since no such department exists to pilot against today.
5. **"Current agent stack" section**: acknowledge the existing brain-level roster override (`brain-yekdast/Agents Office/agents.json`) that `npm run check`'s own output already reveals, rather than stating no overrides exist.
6. **Task 6**: add a line noting the root `CLAUDE.md`/`unused-seats.md` 6-department scheme as a third source of truth that also needs reconciling, not just the two-source conflict the plan currently frames.
7. **Task 16**: either compute the collision margin separately for Backend Engineering (depth 28→38.4) and Infrastructure & QA (depth 26→38.4), or explicitly state that the single ~4.8-unit figure is a shared worst-case estimate, not a per-department computed result.

Everything else — the Foundation tasks' technical content (checkpointer, policy gate, redaction, `interrupt()`, Redis scheduling, contract tests, E2E smoke, legacy retirement), the API contract table, and the dependency/infra setup — is accurate as written and can proceed once the department-naming correction above is made.
