# Validation Report: `agents-office-implementation.plan.md` vs. the repository

## Assumptions
- "Current repository state" means the working tree as checked out right now (git status shows the most recent commit is "Backup: snapshot working tree before 8-department/80-seat Citadel redesign" — i.e., a snapshot taken *before* a redesign was applied, with no later commit showing the redesign landing).
- Where the plan cites a line range loosely (e.g. "47-65"), I treat it as accurate if the named function/block falls within or very near that range, and flag it only when the content at that range doesn't match the claim at all.

## Headline finding: the plan's department baseline is factually wrong, and this invalidates most of Part II

The plan states, in its own merge note (line 12) and repeats as load-bearing throughout: *"Department names and count (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current."* This is false.

The actual department set in the repository right now — checked in three independent places that all agree with each other and disagree with the plan — is `exec`, `revenue`, `engineering`, `frontend`, `devops`, **`secdata`**, `fin`, **`content`**:

- `backend/app/mcp.py:16` — `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`
- `src/data.js:17` — `export const DEPT_KEYS = ['exec', 'revenue', 'engineering', 'frontend', 'devops', 'secdata', 'fin', 'content'];` (and `LAYOUT`/`BILLBOARDS`/`APPROVAL_ASKS` at `src/data.js:80-113` all key off this same set)
- `office.agents.json` — a live count of the `department` field across all 35 agents gives `{content: 3, devops: 5, secdata: 3, revenue: 8, frontend: 4, exec: 3, fin: 3, engineering: 6}`

There is **no `success` and no `product` department anywhere in the current code or config** — not in `mcp.py`, not in `src/data.js`, not in `office.agents.json`, not in `office.agents.local.json` (which doesn't exist), not in `routines.py`'s `ALLOWED = ["content", "fin", "revenue"]`. `success` and `product` are evidently names from the *target* redesign the plan is proposing, but the plan presents them as the **current** baseline in Part I and builds Part II's entire seat-count table, connector matrix remap, and pilot department choice on that false premise.

Consequences that cascade from this one error:
1. **Task 6b is mischaracterized.** The plan says `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, etc. — verified present at `office.config.local.json`, e.g. `"gmail": ["content", "revenue"]`) are *"keyed to an older department scheme that predates the current 8-department roster"* and must be rewritten to `exec/revenue/engineering/frontend/devops/fin/success/product`. In fact `content`/`secdata` **are** the current, live department keys — they match `mcp.py:16`'s `DEPT_KEYS` and `src/data.js`'s `DEPT_KEYS` exactly. There is no drift to fix here; rewriting these keys to `success`/`product` as Task 6b instructs would *break* the config against the actual running code, not fix it.
2. **Task 2's connector matrix is built against departments that don't exist.** The table at lines 83-92 assigns Gmail to `revenue, success` and Notion to `revenue, product, fin` — `success` and `product` are not valid department ids anywhere in the current roster or `mcp.py:DEPT_KEYS`, so this matrix cannot be implemented as written without first deciding whether the rename actually happens.
3. **All of Part II's seat-count table** (`exec` 7, `revenue` 13, `product` 6, `engineering` 14, `frontend` 6, `devops` 14, `success` 5, `fin` 5 = 70, lines 236-246) assumes `product` and `success` already exist as departments to expand. They don't — this is a rename-and-expand, not an expand, and the plan never states that the rename itself (`secdata`→`success`?, `content`→`product`?, or some other mapping) is an in-scope task. No task in Part II performs or even mentions this rename. Task 11's pilot department is stated as "`success` (5-seat cap)" — today there are zero agents in a `success` department (`content` has 3, there is no `success` key at all), so "pilot department = `success`" cannot mean "grow the existing `success` department to 5" the way it's framed next to the Foundation section's "35 seats today" framing.
4. This also means the plan is internally inconsistent with itself: Part I's "ground truth" section asserts the 8-dept scheme including `success`/`product` is already applied, while Part II's "80-seat expansion math (superseded) → 70-seat target" section implies there was an *earlier, now-frozen* redesign attempt — which matches what the repo actually shows (a backup commit taken "before" a redesign, with the redesign evidently not committed). The plan's own history section is closer to the truth than its "ground truth" section; the two contradict each other.

**This is the single most consequential finding in this review** — it means nobody can start Task 11 (or really any Part II task) as written without first resolving what actually happened to the `secdata→?`/`content→?` rename, because the plan assumes it's done and the repo shows it isn't.

## Overall verdict

1. Re-run `npm run check` and confirm whether the 34/38-vs-37/38 discrepancy is flakiness or a real regression before treating "37/38, one known failure" as ground truth.
2. Fix the `test_api_contract.py` classification (UPDATE/extend, not CREATE) and have Task 7 start from an audit of the existing 310-line file rather than writing it fresh; also reconcile the legacy-file count in Task 9's table (8 engine siblings + serve.mjs, not 7) before that delete step runs.

**Part II (Org Redesign) is not safe to start as written.** Its entire premise — that the current roster already uses `exec/revenue/engineering/frontend/devops/fin/success/product` as its 8 departments — is false. The repository's actual current departments are `exec/revenue/engineering/frontend/devops/secdata/fin/content`, confirmed identically in `backend/app/mcp.py:16`, `src/data.js:17` (plus its `LAYOUT`/`BILLBOARDS`/`APPROVAL_ASKS` tables), and a live count of `office.agents.json`. Before any Part II task runs:
- The plan needs an explicit task (missing today) that either (a) states the `secdata→?`/`content→?`→`success`/`product` rename is itself part of this work and specifies the mapping, or (b) corrects every reference to `success`/`product` back to the department names that actually exist, and re-derives the 70-seat table, Task 2's connector matrix, and Task 11's pilot-department choice against real names.
- Task 10's actual dependency on Task 6 (via the `graph/engine.py` state machine it reuses) should be added to Part II's stated gate ("Tasks 1 and 2 only") or to the Org Redesign Acceptance checklist, since as written a team could legitimately start Task 10 after only Tasks 1-2 land and then discover Task 6's state machine doesn't exist yet.
- Task 6b's description of `content`/`secdata` as "stale, pre-redesign" keys needs to be corrected — they're the live keys; it's `success`/`product` that aren't wired to anything in the code today.

The UI/layout math in Task 16 is self-consistent and the plan is appropriately honest about what's still open (plinth width, the starting-margin figure's provenance) — that part doesn't need correction before Task 17, just the already-flagged follow-up work.
