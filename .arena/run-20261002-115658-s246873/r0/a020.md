# Validation Report: `agents-office-implementation.plan.md` vs. current repo state

## Headline finding (breaks almost everything downstream)

The plan's single most load-bearing claim — "Department names and count (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout" (line 12) — **is false**. The repo's actual current department keys, confirmed in three independent places, are:

```
exec, revenue, engineering, frontend, devops, secdata, fin, content
```

- `backend/app/mcp.py:16`: `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`
- `office.agents.json` seat counts by department: `revenue:8, engineering:6, devops:5, frontend:4, content:3, secdata:3, exec:3, fin:3` (35 total)
- `src/data.js` `LAYOUT` and `BILLBOARDS` objects: keyed `exec, revenue, engineering, frontend, devops, secdata, fin, content` — no `success` or `product` key exists anywhere in the frontend either.

There is no department called `success` or `product` anywhere in the current code. The plan uses `success`/`product` as if they already exist today (Part II's target-cap table, Task 11's "pilot department is `success`", the connector matrix in Task 2 which lists `success`/`product` as current department targets). It never states the `content→?` / `secdata→?` rename mapping it repeatedly says it's using ("using the same old→new mapping used elsewhere in this plan" — Task 6b; "re-derive their current department... e.g. an agent that was `sales` is now `revenue`" — Task 6). **No such mapping table exists anywhere in the document.** This is a real, unresolved gap, not a cross-reference I failed to find — I read the full plan text and no old→new department table appears.

This also means: Task 11's pilot target ("`success` (5-seat cap)") cannot be executed as written — there is no `success` department to build toward; someone has to first decide whether `content` or `secdata` becomes `success`, and that decision isn't in the plan.

Compounding this, **`.claude/CLAUDE.md`** (checked into the repo, read as part of this validation) describes a *third*, older taxonomy: 6 departments (`emails`, `sales`, `marketing`, `ops`, `fin`, `delivery`), 35 seats, department caps (5/6/7/6/4/7). This is neither the plan's 8-dept scheme nor the actual repo's 8-dept scheme. Three different department vocabularies (CLAUDE.md's 6, the plan's 8 with `success`/`product`, the repo's actual 8 with `secdata`/`content`) are now live in the project's own guidance documents, and the plan does not acknowledge CLAUDE.md's mismatch at all.

## Overall verdict

**Not a reliable basis to start executing Task 1 onward right now, without corrections.** Most of the deep, specific file/line/code claims (the majority of the document, by volume) are verified accurate — the engine, config, API contract, and dependency claims are a genuinely careful, line-correct audit. But two load-bearing problems need to be fixed before anyone executes against this document:

1. **The department-naming mismatch.** The plan's "current" department set (`exec, revenue, engineering, frontend, devops, fin, success, product`) does not match the repo's actual current department set (`exec, revenue, engineering, frontend, devops, secdata, fin, content`) in `office.agents.json`, `mcp.py:16`, and `src/data.js`'s `LAYOUT`/`BILLBOARDS`. Every task that names `success` or `product` as if it exists today (Task 2's connector matrix, Task 11's pilot target, the 70-seat target table) needs either (a) an explicit old→new rename decision + mapping table added to the plan before Task 6/6b/11 can be executed, or (b) correction to use the real current names (`secdata`, `content`) until that rename actually happens. **Fix: add the missing mapping table (which old department becomes `success`, which becomes `product`) to the plan, in the section right after line 12, before any task that depends on it.**
2. **The `npm run check` baseline.** Line 20's "37/38 passed, one unrelated failure" should be corrected to the actual current result (**33/38**, five failures: the four interactive smoke-test failures listed in §2, plus the one `/api/brain` failure the plan already accounts for). Someone starting Task 7 (contract tests) or Task 9 (legacy retirement, which explicitly gates on "everything above" passing) needs the real number, not a four-months-stale one, to know what "still green" means.

Secondary, lower-stakes corrections: fix Task 6b's framing (the `secdata`/`content` keys in `office.config.local.json` are the *real current* names, not a predates-the-redesign artifact, until the rename mapping above is settled); fix the Files-to-Change table's `CREATE` marking on `test_api_contract.py` to `UPDATE` (it already exists); and flag Task 16's "~10 unit margin, computed explicitly" claim as not actually traceable to any stored value in `src/data.js`/`src/main.js` — it should be re-labeled as an estimate pending real measurement, not presented as already computed from code.

None of this invalidates the scope decision (35→70 seats) or the Foundation engine work, which the task explicitly says is out of bounds to re-litigate — these are corrections to the plan's stated facts about the repo, not to its goals.
