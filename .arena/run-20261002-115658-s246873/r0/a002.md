## 2. Required corrections — these are real problems

### A. The plan's "current 8-department" premise is false. The redesign it describes as already-landed hasn't landed.

The plan's header states: *"Department names and count (8: `exec`, `revenue`, `engineering`, `frontend`, `devops`, `fin`, `success`, `product`) are current and load-bearing throughout."* This is wrong, checked three independent ways against the live repo:

- `backend/app/mcp.py:16`: `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]` — no `success`, no `product`.
- `office.agents.json`'s actual 35 agents break down as `{revenue:8, engineering:6, devops:5, frontend:4, content:3, secdata:3, exec:3, fin:3}` — again `secdata` and `content`, not `success`/`product`.
- `src/data.js`'s `LAYOUT` and `BILLBOARDS` objects are keyed `exec, revenue, engineering, frontend, devops, secdata, fin, content` — same set, same conclusion.

This lines up with the repo's own git history: the current branch tip is `92de5bd Backup: snapshot working tree before 8-department/80-seat Citadel redesign` — i.e., the working tree was snapshotted and apparently reverted to the pre-redesign state, and the plan was never updated to reflect that revert. The plan is describing a department renaming (`secdata`→`success`, `content`→`product`) that was either undone or never actually applied to the files it cites.

This falsifies two specific downstream claims:

- **Task 6b is diagnosing a bug that doesn't exist (and would create one if executed as written).** The plan says `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, etc.) are "stale... pre-redesign keys that don't match the current 8-department roster," and tells Task 2 to depend on fixing them first. In fact those keys match `DEPT_KEYS` and `office.agents.json` **exactly** — I read `office.config.local.json` directly: `"github": ["engineering","frontend","devops"], "gitlab": [...,"secdata","fin"], "slack": [..."secdata",..."content"], "gmail": ["content","revenue"]`, etc. — every department name used is a real, live department. There is no drift to fix today. Executing Task 6b as written would mean rewriting a currently-correct config file to reference departments (`success`, `product`) that don't exist in the roster, which would actively break Task 2's policy gate rather than fix it.
- **Task 11's "Decided (2026-10-02, owner): pilot department is `success`"** names a department that is not in the roster. Either this decision needs to be re-made against a real department (`secdata` or `content`, whichever the owner actually meant), or the department rename needs to be its own explicit task, landed and verified, before Task 11 can start.
- By extension, Part II's whole "Current department/seat-count target" table (Leadership/`exec` 7, Sales & Marketing/`revenue` 13, **Product/`product` 6**, Backend Engineering/`engineering` 14, Frontend Engineering/`frontend` 6, Infrastructure & QA/`devops` 14, **Customer Support/`success` 5**, Finance/`fin` 5) is only buildable once `product` and `success` exist. Right now they don't. The plan should either (a) add an explicit task renaming `secdata`→(whatever maps to Customer Support) and `content`→`product`/Sales & Marketing-adjacent before Task 9b, or (b) correct the table to use the department names that actually exist and re-derive which of `secdata`/`content` is the real pilot candidate.

**Concrete fix**: in the merge note (plan line ~12), Task 6b, and the Part II department table, replace `success`/`product` with the real current keys `secdata`/`content` — or insert a new task that performs and verifies the rename, gated before Task 9b/10/11, and only then treat `success`/`product` as real.

### B. The "37/38 passed, one unrelated failure" ground-truth claim is stale.

The plan states (twice — "Current agent stack" and "Application audit"): *"`npm run check` passes 37/38 (one pre-existing, unrelated failure: `server: /api/brain has the live graph`)"* and concludes *"No application-breaking defects found."*

I ran `npm run check` fresh against the current repo. Actual result: **34/38 passed**, with four failures, not one:

✗ smoke: department focus opens the chat rail  — rail: left agentOpen
✗ smoke: approval flow reaches the panel  — no waiting row (ada: stuck)

Only the last one is the failure the plan accounts for. The other three are smoke-suite failures the plan never mentions, and they sit directly in the task panel / approval-flow / chat-rail surface area that Foundation Tasks 1, 2, 3, 4, and 7 all touch (Task 7's own rationale is built on "`initTasks()` is an 84-edge god node" — these failures are inside exactly that node's territory). The plan's "no application-breaking defects found" conclusion is no longer true as stated, and Task 7's contract tests (which only cover `/api/*` request/response shape, not this demo-mode smoke behavior) won't catch these.

**Concrete fix**: update the "Current agent stack" and "Application audit" sections to the real count (34/38) and name the three additional failures; decide explicitly whether they're in-scope for Task 7 or need a new task, rather than letting the stale "37/38, one failure" number stand as the baseline anyone starts Task 1 against.
