# Validation report: `agents-office-implementation.plan.md` vs. the current repository

## Assumptions
- "Current state" means the repository on disk right now (git status: clean except the plan file itself and an untracked `.arena/` dir), with `npm run check` run live during this validation.
- Where the plan cites a file:line range, "confirmed" means the cited code exists at that location and does what the plan says; a few-line drift (±3 lines) from legitimate surrounding decorators/whitespace is not flagged as an error on its own.

## Headline verdict

**Do not start executing Task 1 onward on this plan as written.** The plan is accurate and unusually well-cited on almost every *backend code* claim (file/line references for `main.py`, `graph/engine.py`, `mcp.py`, `config.py`, `models.py`, `src/main.js`, `src/tasks.js`, and the graphify stats all check out against the repo). But its account of the **current department scheme** — the fact the entire Org Redesign section (Part II) and one Foundation task (6b) are built on — is factually wrong in a way that invalidates Task 11's premise and misdiagnoses Task 6b's root cause. There is also a concrete, reproducible discrepancy in the "application audit" test-pass numbers. Both need correcting before anyone executes against this document. Details below, organized by the task's numbered categories.

## 2. Structural/roster claims — **this is the plan's most serious defect**

The plan asserts (lines 12, 18, 20, and throughout Part II) that the *current* 8-department scheme is `exec, revenue, engineering, frontend, devops, fin, success, product`, with 35 seats today, en route to 70 seats across those same 8 names.

**This is false.** I read the department keys from three independent sources in the live repo, and all three agree with each other and disagree with the plan:

- `office.agents.json` (the actual 35-agent roster) — department values present: `content` (3 seats: `elead`, `cmail`, `newt`), `devops` (5), `secdata` (3: `kmail`, `comply`, `recon`), `revenue` (8), `frontend` (4), `exec` (3), `fin` (3), `engineering` (6). Total 35, 8 departments — but the set is `{exec, revenue, engineering, frontend, devops, secdata, fin, content}`.
- `backend/app/mcp.py:16` — `DEPT_KEYS = ["exec", "revenue", "engineering", "frontend", "devops", "secdata", "fin", "content"]`.
- `backend/app/roster.py:31-32` — comment explicitly says this list "matches routines.mjs's `DEPT_KEYS` (exec/revenue/engineering/frontend/devops/secdata/fin/content)".
- `src/data.js:17` — `export const DEPT_KEYS = ['exec', 'revenue', 'engineering', 'frontend', 'devops', 'secdata', 'fin', 'content'];`

**`success` and `product` do not appear anywhere in `office.agents.json`, `backend/app/`, or `src/data.js`.** They are not a current department — they are the plan's own *invented target names* for the Org Redesign (Task 17's target table uses `success`/`product` as the renamed form of `secdata`/`content`... but the plan never states that mapping, and instead asserts `success`/`product` as already-current in Part I's "ground truth" section, which Part I never touches or renames).

This has two concrete downstream consequences, not just a labeling nitpick:

- **Task 6b is misdiagnosed.** The plan frames `office.config.local.json`'s `mcp.departments` keys (`content`, `secdata`, plus `github`/`gitlab`/etc.) as "stale, pre-redesign" and says they need to be rewritten to the "current" 8-dept set. I confirmed `office.config.local.json`'s actual content: its `mcp.departments` keys are `content` and `secdata` among others — **these are exactly today's live department names**, not stale leftovers. The thing that's actually wrong is the *plan's* assumed current-department list (which uses `success`/`product`, names that exist nowhere in code). Task 6b as written would have someone "fix" a config file that is currently correct, by renaming it to match department names (`success`, `product`) that don't exist yet, breaking the policy gate instead of fixing it.
- **Task 11's pilot premise doesn't hold.** Task 11 says: "pilot department is `success` (5-seat cap)." There is no `success` department today — the nearest current analogue is `content` (3 seats) or `secdata` (3 seats), neither named `success`, and CLAUDE.md's project-level department list (6 departments: `emails, sales, marketing, ops, fin, delivery`) doesn't have a `success` department either, nor does `.claude/AGENTS.md` (6 departments: `emails, sales, marketing, ops, delivery, fin`, confirmed at `.claude/AGENTS.md:5`). So there are now **three different department-naming schemes in play across the repo's own docs** (CLAUDE.md/AGENTS.md's 6, the actual code's 8 with `content`/`secdata`, and the plan's imagined 8 with `success`/`product`), and Task 11 is written as if picking a pilot department inside an existing, named department — when in fact it requires first deciding which current department (`content`? `secdata`?) corresponds to the plan's `success`, and whether that rename happens before or as part of the pilot. The plan never states this mapping anywhere.

**Net finding for category 2:** every *seat-count* assertion (35 today, 70 target, per-department caps summing to 70) is internally self-consistent and arithmetically correct (7+13+6+14+6+14+5+5=70), but the **department-name claim for "today"** is false, and it's load-bearing (the plan says so explicitly at line 12: "Department names and count... are current and load-bearing throughout"). This single error propagates into Task 6b's fix direction and Task 11's pilot-department choice, both of which need to be corrected before execution.

The plan's own text later concedes this is "tight enough that it should be re-verified... before Task 17," which is the right call — but the "~4.8 units" figure as stated is not reproducible from `LAYOUT` as-is without picking one department and one neighbor, and the plan doesn't say which. Treat the 4.8-unit number as illustrative, not verified, exactly as the plan's own hedge says — but flag that the hedge should be stronger: the number can't currently be checked against a single source because two different current depths exist and the plan doesn't say which one the 10-unit and 4.8-unit figures came from.
